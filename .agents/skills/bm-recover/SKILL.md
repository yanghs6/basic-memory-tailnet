description: Rebuild the Basic Memory VM after it was deleted or became unusable, then restore the latest backup. Use when the VM is deleted, will not start, or its data is corrupted. A merely stopped VM is started, not rebuilt.

# Recover the Basic Memory VM

Each of steps 3 to 6 changes cloud resources or data: ask the user and wait for an OK before every one of them, including the `make vm-bootstrap` in step 4. `.env` belongs to the user and lives in the main checkout: the user edits it, and you must not read it by any means (not with Read, `cat` or anything else). The user also runs every command that needs a terminal prompt (the Tailscale auth key, the restore `yes`) in their own terminal. Never ask for the auth key in chat, never put `TS_AUTHKEY=...` on a command line and never pipe `yes`. Every gcloud command is run by the user and carries `--configuration=bm-personal`.

1. Find out whether the VM is really gone: `make status` fails. Ask the user to check the instance (`gcloud compute instances describe <instance> --zone=us-west1-b --configuration=bm-personal --format='value(status)'`).
   - `TERMINATED` (stopped): do not rebuild; the data is on its disk. The user starts it (`gcloud compute instances start <instance> --zone=us-west1-b --configuration=bm-personal`). The external IP changes after a stop and start, so the user reads the new IP (docs/runbooks/gcp-vm.md, section 5) and updates `BM_VM_PUBLIC_IP` in `.env`. Then run `make status` and `make probe`, add an "Incident log" row if it was a real incident, and stop here.
   - Deleted, will not start, or the data is corrupt: continue with step 2.
   - Anything transient: use `bm-diagnose` instead.
2. Choose the newest backup in the main checkout, not in your worktree: the main checkout is the parent directory of `git rev-parse --path-format=absolute --git-common-dir`. List `<main checkout>/backups/bm-*.tgz` with `ls -t` and take the first. Check that both `<file>.sha256` and `<file>.manifest` exist; `make restore` refuses an archive without either ("checksum file missing", "manifest missing"). If no backup qualifies in the main checkout, tell the user the notes cannot be restored and continue with an empty VM only if they agree. Never conclude "no backup" from inside a worktree.
3. Ask first. The user creates a new VM following `docs/runbooks/gcp-vm.md` (keeping `default-allow-ssh` open to their own IP/32 for now) and removes the old `agent-hub` machine in the Tailscale admin console so the new VM can take the name. GCP instances cannot be renamed, so the user creates the new VM under a different `INSTANCE` name and stops the old one if it still exists; never delete the old instance or its disk before the restore is verified. While two e2-micro VMs or two boot disks exist the free tier can be exceeded (it covers one non-preemptible e2-micro's hours per month and 30 GB-months of standard persistent disk, and a stopped VM's disk still counts), so after the restore is verified the user removes the old VM and its disk soon and checks billing (the "비용 점검" section of docs/runbooks/operations.md). The user then sets the new public IP as `BM_VM_PUBLIC_IP` in `.env` (the user's file; you neither edit nor read it).
4. Ask first. The user creates a new one-off auth key (`docs/runbooks/accounts.md`). Before bootstrapping, the user follows step 1 of `docs/runbooks/bootstrap.md` (old Tailscale node, `ssh-keygen -R agent-hub` and `ssh-keygen -R <new-public-ip>`; the latter is harmless when no entry exists, and a stale host key for a reused public IP makes the bootstrap fail with "upload failed"). The user runs `make vm-bootstrap HOST=<new-public-ip>` in their own terminal and pastes the key at the hidden prompt, or runs `read -rs TS_AUTHKEY && export TS_AUTHKEY` first and `unset TS_AUTHKEY` afterwards. It is safe to repeat if it fails.
5. Ask first. First Tailscale SSH to the new VM: ask the user to run an interactive `ssh ubuntu@agent-hub true` and accept the new key. Only when that succeeds, ask the user to delete the firewall rule that opens port 22 (`gcloud compute firewall-rules delete default-allow-ssh --configuration=bm-personal`, docs/runbooks/bootstrap.md step 4).
6. Ask first. Before deploying, run `make status`. If `make status` shows a Basic Memory container, compare its image with `grep 'image:' compose.yaml`; when they differ, stop and ask the user (an unmerged upgrade may be live, see `bm-upgrade`). On a VM where nothing is deployed yet, `make status` ends with `could not query containers`; that is expected, so skip the comparison and only check that `git diff main -- compose.yaml` prints nothing (the next sentence). Run `make deploy` from your worktree only after `git diff main -- compose.yaml` prints nothing (your pin equals main's); if it prints anything, stop and ask the user. Then the user runs `make restore BACKUP=<absolute path of the file from step 2>` in their own terminal and types `yes`; the target runs verify at the end.
7. Run `make status` and `make probe`. The firewall was created again, so ask the user to redo the "Exposure audit" in `docs/runbooks/operations.md` and add a row to its "점검 기록" table. Add a row to "Incident log" in the same file (date, cause, backup used, data loss window) and commit it through the `git-workflow` skill.

If the Serve configuration is wrong afterwards, do not edit it by hand; ask the user first. When "Funnel is on for this node" appears, the user turns Funnel off (removes the `funnel` attribute in the Tailscale policy, see "Exposure audit" in `docs/runbooks/operations.md`) before anything else. Then the user runs `make vm-bootstrap HOST=agent-hub` in their own terminal, because it prompts for the auth key. Assumption (confirm in plan 05): once the public port 22 is closed, use `HOST=agent-hub` over Tailscale SSH. `make status` prints a different hint, `make vm-bootstrap HOST=<public-ip>` (scripts/status.sh), which needs the port 22 rule again; prefer `HOST=agent-hub` and say why. Deleting `/srv/basic-memory.prev-*` is for the human only.
