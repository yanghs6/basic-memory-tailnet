## Global Constraints

- Basic Memory image: `ghcr.io/basicmachines-co/basic-memory:0.23.2@sha256:939f1173d96626c280763e14622f2381d49fbbb7db17cae2e832f4f639405643`. Command `basic-memory mcp --transport streamable-http --host 0.0.0.0 --port 8000 --path /mcp`.
- Host port: `127.0.0.1:${BM_PORT:-8737}`. 컨테이너 포트는 8000이다. `127.0.0.1` 외의 주소에는 절대 바인딩하지 않는다.
- VM 경로:
  - 앱: `/opt/basic-memory` (`BM_REMOTE_APP_DIR`)
  - 데이터: `/srv/basic-memory/{knowledge,config}` (`BM_REMOTE_DATA_ROOT`)
  - 컨테이너 UID/GID: `1000`
- Tailscale:
  - 기기 이름은 `bm-node`, 태그는 `tag:bm-server`다.
  - Funnel은 쓰지 않는다. 노출은 `tailscale serve --bg http://127.0.0.1:8737`로만 한다.
  - 인증 키는 `TS_AUTHKEY` 환경변수나 숨김 프롬프트로만 받는다. 로컬과 원격 어디에서도 명령 인자나 디스크에 남기지 않는다. 원격에서는 `/run` tmpfs의 0600 임시 파일로 `--auth-key=file:`에 넘기고 즉시 삭제한다.
- 도구 이미지(digest 고정):
  - `koalaman/shellcheck:v0.11.0@sha256:61862eba1fcf09a484ebcc6feea46f1782532571a34ed51fedf90dd25f925a8d`
  - `mvdan/shfmt:v3.12.0@sha256:307d265ffd25ce832899ae17c93ed5062fc3375c514bba8f52cbf52792735c4d`
  - `bats/bats:1.14.0@sha256:5322b877351fda0cc435de8c6116de7d0a2ec79d7c680132a0ef329a633bc66f`
  - `kcov/kcov:latest@sha256:481289ae32e55e5b733019515acd10948a4f76dfed381765577db909664fc603`
- 스크립트 작성 규칙:
  - `#!/usr/bin/env bash` 다음 줄에 `set -euo pipefail`을 둔다. `scripts/lib/common.sh`는 source만 하므로 예외다.
  - **macOS bash 3.2 호환**: `mapfile`, `readarray`, `declare -A`, `${x,,}`, `inherit_errexit`, 빈 배열 확장을 쓰지 않는다.
  - die할 수 있는 함수를 `x="$(fn)"`로 호출하면 뒤에 `|| exit 1`을 붙인다. bash 3.2는 명령 치환 안에서 errexit를 상속하지 않기 때문이다.
- shfmt 스타일은 `.editorconfig`를 따른다(2칸 들여쓰기, case 들여쓰기, 이항 연산자는 줄 앞). 리디렉션은 공백 없이 `>file`로 쓴다. lint가 포맷 차이를 보고하면 `make fmt`로 고친다.
- shellcheck 예외는 이유와 함께 그 줄 바로 위에만 둔다. trap으로만 호출되는 함수(`cleanup`, `restart_container`)에 SC2317이 나오면 `# shellcheck disable=SC2317  # invoked via trap`을 붙인다. 다른 경고는 코드를 고친다.
- 커버리지: `scripts/` 라인 커버리지 80% 이상. `scripts/` 아래 모든 실행 스크립트는 최소 한 테스트에서 실행돼야 한다.
- 언어:
  - 코드, 주석, 스크립트 메시지, `AGENTS.md`, `SKILL.md`는 영어로 쓴다.
  - README, runbooks, ARCHITECTURE, ADR은 한국어로 쓴다.
  - 저장소 노트에는 `Verified` / `Command` / `Assumption` / `Open question` 표기를 쓴다.
- Git (`docs/specs/2026-10-07-git-review-policy-design.md`):
  - 이 계획은 `plan/04-docs-skills` 브랜치의 전용 worktree에서 진행한다. `main`에 직접 커밋하지 않고, force-push·히스토리 재작성·`git gc`를 하지 않는다.

`.agents/skills/bm-upgrade/SKILL.md`:
```markdown
---
name: bm-upgrade
description: Upgrade the pinned Basic Memory container image (version and digest) and roll it out to the VM safely. Use when asked to update, bump or patch Basic Memory.
---

# Upgrade Basic Memory

This changes what runs against real notes. Follow the steps in order and ask the user before step 6.

1. Current pin: `grep 'image:' compose.yaml`. Keep this line for rollback.
2. Pick the target release on https://github.com/basicmachines-co/basic-memory/releases. Read the notes between the current and target versions for changes to: the `mcp` CLI flags (`--transport streamable-http --path /mcp`), `BASIC_MEMORY_*` env vars, data paths (`/app/data`, `/home/appuser/.basic-memory`), and the tools `write_note`, `read_note`, `search_notes`, `delete_note`. Flag any database, index or config migration: once the new version touches the data, the old image must not run on it again. Summarize all of this for the user.
3. Resolve the multi-arch digest (image tags have no `v` prefix) and confirm arm64 is included:
   `docker buildx imagetools inspect ghcr.io/basicmachines-co/basic-memory:<version>`
   Use the `Digest:` line of the index and check the list contains `linux/arm64`.
4. Change only the `image:` line in `compose.yaml` to `ghcr.io/basicmachines-co/basic-memory:<version>@<digest>`.
5. Verify locally: `make check local-up local-verify`, then `make local-down`. If anything fails, stop and report; do not deploy.
6. Ask the user to approve the rollout. Run `make backup` and record the archive name: it is the rollback point. Then run `make deploy verify status`.
7. To roll back, never just redeploy the old image: tell the user that notes written after step 6 will be replaced (they stay in `/srv/basic-memory.prev-*`), put the old `image:` line back, then run `make restore BACKUP=<archive from step 6>` (user types yes). Restore applies this repo's compose.yaml together with the backed-up data and then runs verify.
8. Commit `compose.yaml` as `chore: upgrade basic-memory to <version>` and record the outcome (Verified/Command) in the active plan or a new ADR.
```

`.agents/skills/bm-recover/SKILL.md`:
```markdown
---
name: bm-recover
description: Rebuild the Basic Memory VM after OCI reclaims it or it becomes unusable, then restore the latest backup. Use when the VM is terminated, permanently unreachable, or its data is corrupted.
---

# Recover the Basic Memory VM

Each step changes cloud resources or data. Confirm with the user before steps 3, 5 and 6.

1. Confirm the VM is really gone: `make status` fails and the user sees the instance stopped or terminated in the OCI console. For anything transient, use `bm-diagnose` instead.
2. Choose the newest backup with a checksum: `ls -t backups/bm-*.tgz | head -n 1` and check `<file>.sha256` exists. If there is none, tell the user the notes cannot be restored and continue with an empty VM only if they agree.
3. The user creates a new VM following `docs/runbooks/oci-vm.md` (temporary port 22 rule) and removes the old `bm-node` machine in the Tailscale admin console so the new VM can take the name. Ask for the new public IP and update `BM_VM_PUBLIC_IP` in `.env`.
4. The user creates a new one-off auth key (`docs/runbooks/accounts.md`). Run `make vm-bootstrap HOST=<new-public-ip>`; the user pastes the key at the prompt.
5. Check `ssh ubuntu@bm-node true`, then ask the user to delete the port 22 ingress rule.
6. Run `make deploy`, then `make restore BACKUP=<file from step 2>`; the user types yes and the target runs verify.
7. Run `make status` and add a row to "Incident log" in `docs/runbooks/operations.md` (date, cause, backup used, data loss window).
```

`.agents/skills/bm-diagnose/SKILL.md`:
```markdown
---
name: bm-diagnose
description: Read-only troubleshooting for the Basic Memory MCP endpoint, Tailscale Serve, Tailscale SSH and the VM container. Use when an agent cannot reach Basic Memory, make verify or make probe fails, or the VM seems unhealthy.
---

# Diagnose Basic Memory

Read-only: run only `tailscale status`, `ssh ubuntu@bm-node true`, `make status`, `make logs`, `make probe` and read-only shell commands on the VM (`ls`, `df`, `cat`). Anything that writes notes, starts or restarts something, or changes settings (`make verify`, `make local-up`, `make deploy`, `make restore`) is a proposal for the user, not a step you run.

Work top-down and stop at the first layer that fails:

1. Tailnet: `tailscale status | grep bm-node` on this machine. Missing or offline: the VM is down or logged out; check the OCI console (terminated means `bm-recover`).
2. SSH: `ssh ubuntu@bm-node true`. Failing while the tailnet is fine: check the Tailscale policy `ssh` rule for `tag:bm-server` (docs/runbooks/accounts.md).
3. Container: `make status`. Not `(healthy)`: run `make logs` and quote the first error.
4. Memory warning from `make status`: idle-reclaim risk; see "Idle reclamation" in docs/runbooks/operations.md.
5. Serve: `make status` must show `proxy http://127.0.0.1:8737`. Missing: bootstrap step `configure_serve` did not run.
6. MCP: `make probe` (initialize and tools/list only; writes nothing) and read the failing step:
   - `initialize: request ... failed`: DNS or HTTPS; check MagicDNS and HTTPS certificates in the Tailscale admin console.
```

````markdown
## 토폴로지

[개인/회사 Mac] ── tailnet ──▶ https://bm-node.<tailnet>.ts.net/mcp

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| `Makefile` + `scripts/` | Mac | 유일한 제어 지점. SSH로 VM을 다룸 |
| `scripts/remote/bootstrap.sh` | VM (root) | Docker·Tailscale 설치, 데이터 디렉터리, Serve 설정 |
| `compose.yaml` | Mac(로컬 검증)·VM | Basic Memory 컨테이너 정의 (같은 파일) |

| Tailscale SSH | VM | 부트스트랩 이후의 유일한 관리 경로 |
| `backups/` | Mac | `make backup` 결과물 (git ignore) |

## 데이터 경로

| 데이터 | 로컬 | VM |
|---|---|---|
| Markdown 노트 | `.local-data/knowledge/basic-memory/` | `/srv/basic-memory/knowledge/basic-memory/` |

| compose와 `.env` | 저장소 루트 | `/opt/basic-memory/` |

기본 프로젝트 `main`은 `/app/data/basic-memory`에 생성됩니다(**Verified**, 0.23.2).

## 신뢰 경계

- Basic Memory에는 인증이 없습니다(**Verified**). 접근 제어는 전적으로 Tailscale의 기기 인증과 정책에 맡깁니다.
- 컨테이너 포트는 `127.0.0.1`에만 바인딩하고, Serve는 tailnet 전용(Funnel off)이며, OCI 공개 인바운드 규칙은 0개입니다.
- 자동 검증 범위: `tests/repo.bats`(설정 파일)와 `make verify`/`make probe`(바인딩, Serve 상태, 공인 IP의 22·80·443·8737). OCI 인바운드 규칙과 tailnet 정책은 VM에서 읽을 수 없어 [운영 런북](runbooks/operations.md)의 Exposure audit으로 수동 점검합니다.
- 비밀값은 Tailscale 인증 키 하나뿐이며, 저장소와 디스크에 남지 않습니다.

## 주요 흐름

- **배포:** `make deploy` → compose와 VM용 `.env` 전송 → `docker compose pull` → `up -d --wait`
- **검증:** `make verify` → tailnet URL로 MCP 왕복(initialize, tools/list, 쓰기·읽기·삭제) → 포트 바인딩 → Serve tailnet 전용 → 공인 IP 포트 차단. `make probe`는 같은 검사를 노트 쓰기 없이 합니다.
- **백업:** `make backup` → (재시작 예약) 컨테이너 정지 → 파일별 체크섬 manifest → `/srv/basic-memory`를 tar로 받아옴 → 컨테이너 재시작 → sha256 저장
- **복원:** `make restore` → 정지 → 임시 경로에 압축 해제 → manifest 대조 → 저장소 compose.yaml 적용 → 데이터 교체(기존은 `.prev-*`) → 기동 → verify. 정지 이후 실패하면 이전 데이터와 compose로 자동 롤백
````

````markdown
}
````

````markdown
# VM 만들기 (gcloud)

이 런북의 명령은 사용자가 자기 터미널에서 실행합니다. 에이전트는 VM, 방화벽, 클라우드 자원을 바꾸는 명령을 사용자의 OK 없이 실행하지 않습니다. 이 Mac의 활성 gcloud 설정은 회사 계정일 수 있으므로, **모든 gcloud 명령에 `--configuration=bm-personal`을 붙입니다**([accounts 1단계](accounts.md)).

## 0. 변수와 설정 확인

```bash
INSTANCE=agent-hub-01   # GCP 인스턴스 이름. Tailscale 기기 이름(bm-node)과 달라도 됩니다.
ZONE=us-west1-b
gcloud config list --configuration=bm-personal
```

Expected: `account`가 개인 계정이고 `project`가 이 저장소 전용 프로젝트입니다. 회사 계정이나 회사 프로젝트가 보이면 **여기서 멈추고** [accounts 1단계](accounts.md)를 다시 합니다.

옛 인스턴스가 아직 남아 있는 재구축이라면 `INSTANCE`에 다른 이름을 씁니다(옛 VM은 복원이 검증된 뒤에 지웁니다).

## 1. SSH 키

키가 없으면 만듭니다: `ssh-keygen -t ed25519`. 공개키는 `~/.ssh/id_ed25519.pub`입니다. 인스턴스 메타데이터에는 **공개키만** 둡니다.

**Verified (docs.cloud.google.com/compute/docs/connect/add-ssh-keys):** OS Login을 켜지 않았다면 VM은 메타데이터의 SSH 키를 씁니다. OS Login을 켜면 메타데이터 키는 무시됩니다. **Verified (2026-10-12, Command: `gcloud compute project-info describe --configuration=bm-personal`):** 이 프로젝트의 메타데이터에는 `enable-oslogin`이 없습니다. 아래 4단계에서 다시 확인합니다.

## 2. 인스턴스 생성

무료 조건을 명령에 고정합니다(**Verified**, docs.cloud.google.com/free/docs/free-cloud-features, 2026-10-12).

| 항목 | 값 | 이유 |
|---|---|---|
| 머신 | `e2-micro` (1GB) | 월 1대 무료 |
| 리전·존 | `us-west1-b` | 무료 리전(us-west1, us-central1, us-east1) 중 한국에서 가장 가까움 |
| 이미지 | `ubuntu-minimal-2604-lts-amd64` (프로젝트 `ubuntu-os-cloud`, X86_64) | **Verified** (2026-10-12, Command: `gcloud compute images describe-from-family ubuntu-minimal-2604-lts-amd64 --project=ubuntu-os-cloud --configuration=bm-personal`) |
| 부트 디스크 | `pd-standard` 30GB | 월 30GB 표준 영구 디스크 무료. balanced 디스크는 무료가 아님 |
| 프로비저닝 | `STANDARD` | Spot(preemptible) VM은 무료가 아님 |
| 네트워크 티어 | `PREMIUM`, ephemeral 외부 IPv4 | 기본값 |
| 관리자 계정 | 메타데이터 `ssh-keys=ubuntu:<공개키>` | GCP 게스트 에이전트가 `ubuntu`를 만듭니다. 스크립트의 `ADMIN_USER=ubuntu`를 그대로 씁니다 |

새 프로젝트는 Compute Engine API가 꺼져 있을 수 있습니다. 먼저 켭니다(이미 켜져 있으면 아무 일도 하지 않습니다). **Assumption:** API를 켜면 `default` 네트워크와 기본 방화벽 규칙이 만들어집니다.

```bash
gcloud services enable compute.googleapis.com --configuration=bm-personal
gcloud compute instances create "$INSTANCE" --configuration=bm-personal \
  --zone="$ZONE" --machine-type=e2-micro \
  --image-family=ubuntu-minimal-2604-lts-amd64 --image-project=ubuntu-os-cloud \
  --boot-disk-type=pd-standard --boot-disk-size=30GB \
  --provisioning-model=STANDARD --network-tier=PREMIUM \
  --metadata=ssh-keys="ubuntu:$(cat ~/.ssh/id_ed25519.pub)"
```

Expected: 인스턴스가 `RUNNING`으로 만들어지고 `EXTERNAL_IP`가 한 줄 보입니다.

**Assumption (계획 05에서 확인):** 26.04 Minimal에 `ss`(iproute2)와 `free`(procps)가 기본으로 있고, 메타데이터 키로 만든 `ubuntu`에게 암호 없는 sudo가 있습니다.

## 3. 방화벽 정리

`default` 네트워크에는 `default-allow-ssh`(tcp:22), `default-allow-rdp`(tcp:3389), `default-allow-icmp`가 `0.0.0.0/0`으로, `default-allow-internal`이 `10.128.0.0/9`로 미리 들어 있습니다(**Verified**, docs.cloud.google.com/firewall/docs/firewalls). 규칙이 없으면 인바운드는 모두 차단됩니다.

```bash
gcloud compute firewall-rules delete default-allow-rdp default-allow-icmp --configuration=bm-personal
MY_IP="$(curl -4 -s https://ifconfig.me)"
gcloud compute firewall-rules update default-allow-ssh --source-ranges="$MY_IP/32" --configuration=bm-personal
```

재구축처럼 규칙이 이미 지워진 프로젝트에서는 `delete`가 "not found"로 실패하고 `update`도 실패합니다. 이때 rdp·icmp 삭제는 건너뛰고, 22번 규칙은 새로 만듭니다.

```bash
gcloud compute firewall-rules create default-allow-ssh --configuration=bm-personal --network=default --direction=INGRESS --allow=tcp:22 --source-ranges="$MY_IP/32"
```

- `default-allow-internal`은 VPC 내부 전용이라 둡니다. 8737과 443은 열지 않습니다.
- `default-allow-ssh`는 [부트스트랩](bootstrap.md)에서 Tailscale SSH를 확인한 **뒤에** 지웁니다.
- 다른 네트워크에서 부트스트랩하면 내 IP가 바뀌므로 위 `update` 명령을 다시 실행합니다.
- 이 명령들은 [운영 런북](operations.md)의 Exposure audit 기준(VPC 밖 소스를 허용하는 인바운드 규칙 0개)을 만족시키기 위한 것입니다. 마지막 확인은 거기서 합니다.

## 4. 생성 결과 확인

```bash
gcloud compute instances describe "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --format='value(scheduling.provisioningModel,machineType.basename(),networkInterfaces[0].accessConfigs[0].networkTier)'
gcloud compute disks describe "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --format='value(type.basename(),sizeGb)'
gcloud compute project-info describe --configuration=bm-personal --format='value(commonInstanceMetadata.items)'
```

Expected:
- 첫 명령: `STANDARD`, `e2-micro`, `PREMIUM`. `SPOT`이 나오면 6단계로 갑니다.
- 둘째 명령: `pd-standard`와 `30`. **Assumption:** 부트 디스크 이름은 인스턴스 이름과 같습니다.
- 셋째 명령 출력에 `enable-oslogin`이 없습니다. `TRUE`로 있으면 메타데이터 키가 무시되므로 먼저 해결합니다.

## 5. 공인 IP 기록, 정지와 시작

```bash
gcloud compute instances describe "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --format='value(networkInterfaces[0].accessConfigs[0].natIP)'
```

이 값을 main 체크아웃 `.env`의 `BM_VM_PUBLIC_IP`에 적습니다(사용자가 직접 편집). 그다음 [부트스트랩](bootstrap.md)으로 넘어갑니다.

**Verified (2026-10-12, 실제 프로젝트):** 정지 후 시작하면 ephemeral 외부 IP가 바뀝니다. **Assumption (계획 05에서 확인):** 게스트 OS 재부팅으로는 바뀌지 않습니다.

```bash
gcloud compute instances stop "$INSTANCE" --zone="$ZONE" --configuration=bm-personal
gcloud compute instances start "$INSTANCE" --zone="$ZONE" --configuration=bm-personal
gcloud compute instances describe "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --format='value(status)'
```

- 정지된 VM의 `status`는 `TERMINATED`입니다. 시작한 뒤에는 위 IP 조회 명령으로 새 IP를 읽어 `.env`의 `BM_VM_PUBLIC_IP`를 바꿉니다. `verify`가 옛 IP로 검사하지 않게 하려면 이 값을 반드시 맞춰 둡니다.
- 정지된 VM은 지우거나 다시 만들지 않고 시작합니다. 디스크의 데이터가 그대로 있습니다([운영 런북](operations.md)).

## 6. Spot으로 잘못 만든 경우

`set-scheduling --provisioning-model=STANDARD`는 Spot VM에서 `preemptionNoticeDuration` 오류로 실패합니다(**Verified**, 2026-10-12, 실제 프로젝트). 대신 내보내기 → 수정 → 갱신으로 바꿉니다.

```bash
gcloud compute instances stop "$INSTANCE" --zone="$ZONE" --configuration=bm-personal
EXPORT_FILE="${TMPDIR:-/tmp}/$INSTANCE.yaml"
gcloud compute instances export "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --destination="$EXPORT_FILE"
```

`$EXPORT_FILE`의 `scheduling:` 블록을 다음으로 바꿉니다. **Assumption:** Spot 전용 항목(`instanceTerminationAction`, `preemptionNoticeDuration` 등)이 남아 있으면 지웁니다.

```yaml
scheduling:
  automaticRestart: true
  onHostMaintenance: MIGRATE
  preemptible: false
  provisioningModel: STANDARD
```

```bash
gcloud compute instances update-from-file "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --source="$EXPORT_FILE" --most-disruptive-allowed-action=RESTART
gcloud compute instances start "$INSTANCE" --zone="$ZONE" --configuration=bm-personal
```

그다음 4단계로 다시 확인하고, 5단계로 새 IP를 기록합니다. 내보낸 파일은 저장소에 두지 않습니다.

## 7. 재구축할 때의 정리

VM을 다시 만드는 경우 옛 인스턴스와 디스크는 **복원이 검증되기 전에는 지우지 않습니다**. 복원 검증 뒤에 지울 때는 사용자가 직접 인스턴스 삭제 명령을 실행합니다(`--configuration=bm-personal`을 붙이고 `--zone`을 확인). 전체 순서는 [운영 런북](operations.md)의 "VM 재구축 순서"에 있습니다.
````

````markdown
# ADR 0001: Basic Memory를 GCP 무료 e2-micro + Tailscale에 자체 호스팅

- 상태: Accepted (2026-10-12). 2026-10-07의 OCI Always Free 결정을 대체합니다.
- 출처: [설계 스펙](../specs/2026-10-12-basic-memory-gcp-tailscale-design.md)

## 맥락

여러 기기의 에이전트가 같은 Basic Memory를 써야 합니다. 비용은 0원이어야 하고, Basic Memory HTTP 엔드포인트에는 인증이 없습니다(**Verified**).

처음에는 OCI Always Free A1 VM을 골랐지만 만들지 못했습니다. 사용자 콘솔에서 A1 생성이 "Out of capacity for shape VM.Standard.A1.Flex in availability domain AD-1"로 실패했고, 춘천 리전은 A1 자체가 없습니다(**Verified**, docs.oracle.com, Always Free Resources: "…in any availability domain, except South Korea North (Chuncheon)"). 사용자는 무료만 허용합니다.

## 결정

- GCP 무료 등급의 `e2-micro`(us-west1-b, Ubuntu 26.04 LTS Minimal amd64, `pd-standard` 30GB, STANDARD 프로비저닝)에서 Docker로 Basic Memory를 실행하고, Tailscale Serve로 tailnet 안에만 노출합니다.
- VM과 방화벽은 [런북](../runbooks/gcp-vm.md)의 gcloud 명령으로 만듭니다(개인 gcloud 설정 `bm-personal`). 나머지는 이 저장소의 스크립트와 Make 타깃으로 처리합니다.
- 공인 SSH는 부트스트랩에만 쓰고 이후 Tailscale SSH로 전환하며, VPC 밖 소스를 허용하는 인바운드 규칙을 두지 않습니다.

## 대안

- **OCI Always Free A1:** 위 맥락의 이유로 만들 수 없었습니다.
- **AWS:** 신규 계정 무료 기간이 최대 6개월입니다.
- **Koyeb Free:** 영구 볼륨을 쓸 수 없습니다.
- **Basic Memory Cloud:** MCP 엔드포인트에 유료 구독이 필요합니다.

## 결과

- RAM이 1GB로 고정이라 스왑 1GB를 부트스트랩이 만듭니다([ADR 0002](0002-vm-sizing.md)).
- 무료 리전이 미국뿐이라 한국에서는 지연이 큽니다.
- 정지 후 시작하면 외부 IP가 바뀝니다. 런북이 IP 조회와 `.env` 갱신을 안내합니다.
- 외부 IPv4 요금($0.005/h, 2024-02-01부터)이 무료 등급에 포함되는지는 공식 문서에 없습니다(**Open question**). 배포 다음 날 청구 보고서를 SKU별로 확인합니다([운영 런북](../runbooks/operations.md)의 비용 점검).
- Tailscale 계정이 단일 장애점이 됩니다. 대신 인증 없는 엔드포인트가 인터넷에 노출되지 않습니다.
````

````markdown
# ADR 0002: VM 크기 (e2-micro 1GB + 스왑 1GB)

- 상태: Proposed (2026-10-12). 계획 05에서 VM 실측 후 Accepted로 바꿉니다.

## 맥락

GCP 무료 등급의 VM은 `e2-micro`(1GB)뿐이고 크기를 바꿀 수 없습니다. 이 호스트에는 유휴 VM을 거두어 가는 정책이 없으므로 메모리를 일부러 채울 필요가 없습니다. 반대로 1GB는 컨테이너, dockerd, tailscaled, OS를 함께 올리기에 빠듯합니다.

## 근거

- **Verified (2026-10-07, Command: `docker stats --no-stream`):** 0.23.2 컨테이너 메모리 사용량은 기동 직후 212 MiB, `search_notes` 실행으로 임베딩 모델이 올라간 뒤 449 MiB입니다(Mac Docker Desktop 기준, arm64 이미지). VM은 amd64이므로 수치가 다를 수 있습니다(**Assumption**).
- **Assumption:** Ubuntu 26.04 Minimal + dockerd + tailscaled의 기본 사용량은 아직 재지 않았습니다. 계획 05에서 `make status`로 측정합니다.
- 산수: 임베딩 모델이 올라간 컨테이너만으로 449 / 1024 ≈ 44%입니다. 나머지 약 575 MiB에 OS, dockerd, tailscaled가 들어가야 하므로 여유가 작습니다. 그래서 스왑 파일 1GB를 둡니다.

## 결정

`e2-micro` 그대로 쓰고, 부트스트랩이 `/swapfile` 1GB를 만듭니다(Docker 설치 전, 이미 있으면 건너뜀). `make status`는 활성 스왑이 없으면 경고합니다.

## 재평가 기준

- 계획 05에서 배포 24시간 뒤, `make backup`으로 컨테이너를 재시작하고 `search_notes`로 임베딩 모델을 올린 상태에서 `make status`의 메모리·스왑 사용량을 기록합니다.
- 컨테이너가 OOM으로 재시작되거나(`make logs`, `make status`), 스왑 사용이 스왑 크기의 절반 이상으로 계속 유지되면 사용자가 결정합니다. 선택지는 현재 크기를 감수하는 것, 유료 소형 인스턴스(비용 발생), 다른 호스트입니다. **Assumption:** "스왑 크기의 절반 이상"이라는 기준값은 측정 후 조정합니다.
- 측정 결과를 이 ADR에 Verified로 추가하고 상태를 Accepted로 바꿉니다.
````

````markdown
# 부트스트랩: VM을 tailnet에 올리고 배포하기

`make vm-bootstrap`, `make deploy`, `make restore`는 VM을 바꾸므로 에이전트는 사용자의 OK를 받은 뒤에만 실행합니다. 인증 키 프롬프트처럼 터미널 입력이 필요한 명령은 사용자가 자기 터미널에서 직접 실행합니다.

## 준비

- `.env`는 main 체크아웃에 있습니다([accounts 3단계](accounts.md)). `BM_TAILNET_DOMAIN`과 `BM_VM_PUBLIC_IP`가 채워져 있는지 사용자가 확인합니다(에이전트는 읽을 수 없음). 없으면 main 체크아웃에서 `cp .env.example .env` 후 채웁니다.
- 사람은 VM 대상 Make 타깃을 main 체크아웃에서 실행합니다. 에이전트는 자기 worktree에서 실행해도 되며, 그때도 `.env`와 `backups/`는 main 체크아웃의 것을 씁니다. 에이전트가 worktree에서 `deploy`·`restore`를 할 때는 먼저 `git diff main -- compose.yaml`이 아무것도 출력하지 않는지 확인합니다.
- [accounts 런북 5단계](accounts.md)대로 1회용 인증 키를 **지금** 발급합니다(만료 1일).

## 순서

1. VM을 다시 만드는 경우(재구축)에만 먼저:
   - Tailscale admin console에서 옛 `bm-node` 기기를 삭제합니다. 남아 있으면 새 노드가 `bm-node-1` 같은 다른 이름으로 들어옵니다.
   - 옛 호스트 키를 지웁니다: `ssh-keygen -R bm-node`
   - 새 VM의 공인 IP가 옛 IP와 같을 수 있으므로 `ssh-keygen -R <새 공인 IP>`도 실행합니다(항목이 없어도 무해합니다). 남아 있으면 `make vm-bootstrap`이 `upload failed`로 끝납니다.
2. `make vm-bootstrap HOST=<공인 IP>` → 숨김 프롬프트에 인증 키를 붙여 넣습니다(화면에 표시되지 않음).
   - 인증 키를 명령줄에 쓰지 마세요(`make vm-bootstrap TS_AUTHKEY=...` 금지: 셸 기록과 프로세스 목록에 남습니다). 프롬프트를 쓰거나, 먼저 `read -rs TS_AUTHKEY && export TS_AUTHKEY`를 실행합니다. 이 경우 끝나면 같은 셸에서 `unset TS_AUTHKEY`를 실행합니다(그 셸에서 나중에 띄운 도구가 키를 물려받지 않게).
   - 스왑 파일 1GB(`/swapfile`)를 **가장 먼저** 만들고(Docker 설치 전), Docker·Tailscale 설치, tailnet 참여(`bm-node`, Tailscale SSH), 데이터 디렉터리 생성, Serve 설정까지 합니다.
   - 여러 번 실행해도 안전합니다. 이미 tailnet에 있으면 키 없이 빈 입력으로 다시 실행할 수 있고, 스왑이 이미 있으면 건너뜁니다.
3. `ssh ubuntu@bm-node true` → **대화형으로 처음 한 번** 실행해 새 호스트 키를 수락하고, Tailscale SSH로 접속되는지 확인합니다.
4. **3단계가 성공한 뒤에만** 22번을 여는 방화벽 규칙을 지웁니다.

   ```bash
   gcloud compute firewall-rules delete default-allow-ssh --configuration=bm-personal
   ```

   이제 VPC 밖 소스를 허용하는 인바운드 규칙이 없습니다(`default-allow-internal`의 `10.128.0.0/9`만 남음).
5. `make deploy verify status`

## 완료 조건

- [ ] `make verify`가 `OK: MCP round trip passed`, `listens on 127.0.0.1 only`, `tailscale serve is tailnet only`, `refuses ports 22 80 443 8737`을 모두 출력한다.
- [ ] [운영 런북](operations.md)의 Exposure audit(수동 점검)을 마치고 결과를 기록했다.
- [ ] `make status`에 `(healthy)`, `proxy http://127.0.0.1:8737`이 보이고, 스왑이 활성이다(`no active swap` 경고가 없음).
- [ ] `make backup`이 main 체크아웃의 `backups/`에 `bm-*.tgz`와 `.sha256`, `.manifest`를 만든다.
````

````markdown
# 운영

사람은 VM 대상 Make 타깃(`deploy`, `verify`, `backup`, `restore` 등)을 main 체크아웃에서 실행합니다. 에이전트는 자기 worktree에서 실행해도 되며, 그때도 `.env`와 `backups/`는 main 체크아웃의 것을 씁니다. 에이전트가 worktree에서 `deploy`·`restore`를 할 때는 먼저 `git diff main -- compose.yaml`이 아무것도 출력하지 않는지 확인합니다(아래 "배포·복원 전 이미지 확인"도 함께).

## 일상 명령

| 목적 | 명령 |
|---|---|
| 상태 점검 (주 1회) | `make status` |
| 읽기 전용 검사 (노트를 쓰지 않음) | `make probe` |
| 종단 검증 (테스트 노트를 쓰고 지움) | `make verify` |
| 로그 | `make logs` |
| 배포 (compose 변경 후) | `make deploy verify` |
| 백업 (주 1회 + 업그레이드 전) | `make backup` |
| 복원 | `make restore BACKUP=<백업 파일의 절대 경로>` (사용자가 자기 터미널에서 `yes` 입력. 저장소의 compose.yaml도 함께 적용하고, 실패하면 이전 상태로 자동 롤백, 끝나면 verify 실행) |

에이전트는 `vm-bootstrap`, `deploy`, `restore` 전에 사용자의 OK를 받습니다. `probe`, `status`, `logs`, `verify`, `backup`은 OK 없이 실행할 수 있습니다(`verify`는 테스트 노트를 쓰고 지우며, `backup`은 컨테이너를 잠깐 멈춥니다).

**배포·복원 전 이미지 점검:** `make status`의 컨테이너 이미지와 `grep 'image:' compose.yaml`이 같은지 확인합니다. 다르면 멈추고 사용자에게 묻습니다. 업그레이드 리뷰 중에는 VM이 main이 고정하지 않은 이미지로 돌 수 있고, 이때 옛 이미지를 새 버전이 손댄 데이터 위에 배포하면 안 되기 때문입니다([bm-upgrade 스킬](../../.agents/skills/bm-upgrade/SKILL.md)).

## 백업

- 결과물은 main 체크아웃의 `backups/`에 저장됩니다(git ignore, worktree에서 실행해도 같음). Time Machine 등으로 Mac 밖에도 사본을 두세요.
- worktree를 지우기 전에 그 안에 `backups/`가 없는지 확인합니다. `git worktree remove`는 git ignore 파일을 경고 없이 지웁니다.
- 백업 중에는 컨테이너가 몇 초 멈춥니다. SQLite 파일이 쓰는 도중에 복사되지 않게 하기 위해서입니다.
- 백업마다 `.sha256`(아카이브 무결성)과 `.manifest`(데이터 파일별 체크섬)가 함께 저장됩니다. 둘 중 하나라도 없으면 `make restore`가 거부합니다.
- 복원은 임시 경로에 먼저 풀고 manifest와 대조한 뒤에만 교체합니다. 기존 데이터는 `/srv/basic-memory.prev-<시각>`으로 옮겨지고, 실패하면 자동으로 되돌아갑니다(실패한 복원본은 `.failed-<시각>`에 남음).
- `.prev-*`와 `.failed-*` 삭제는 **사람만** 합니다. 에이전트는 지우지 않습니다. 결과를 확인한 뒤 직접: `ssh ubuntu@bm-node sudo rm -r /srv/basic-memory.prev-<시각>`

## 업그레이드·복구·진단

에이전트에게 스킬을 쓰라고 요청합니다.
- 업그레이드: `bm-upgrade`
- VM이 삭제됐거나 쓸 수 없을 때(정지만 된 VM은 아래 "정지된 VM"): `bm-recover`
- 연결·MCP 문제: `bm-diagnose` (읽기 전용)

## 정지된 VM

VM이 정지돼 있으면(`TERMINATED`) 다시 만들지 않고 시작합니다. 디스크의 데이터가 그대로 있어서, 재구축하면 마지막 백업 이후의 노트를 잃습니다.

1. 사용자가 상태를 확인하고 시작합니다. 새 셸이면 먼저 [gcp-vm.md](gcp-vm.md) 0단계의 `INSTANCE`, `ZONE`을 설정합니다.

   ```bash
   gcloud compute instances describe "$INSTANCE" --zone="$ZONE" --configuration=bm-personal --format='value(status)'
   gcloud compute instances start "$INSTANCE" --zone="$ZONE" --configuration=bm-personal
   ```

2. 정지 후 시작하면 외부 IP가 바뀝니다([gcp-vm.md](gcp-vm.md) 5단계의 조회 명령). 새 IP를 `.env`의 `BM_VM_PUBLIC_IP`에 적습니다.
3. `make status`와 `make probe`로 확인합니다. 실제 장애였다면 Incident log에 행을 추가합니다.

## VM 재구축 순서

VM이 삭제됐거나 시작되지 않거나 데이터가 손상됐을 때만 합니다(에이전트의 `bm-recover` 스킬이 같은 순서를 따릅니다).

1. 최신 백업(`.sha256`과 `.manifest` 포함)이 main 체크아웃의 `backups/`에 있는지 확인합니다.
2. [gcp-vm.md](gcp-vm.md)대로 VM을 다시 만들고 방화벽을 정리합니다. 옛 인스턴스와 디스크는 복원이 검증되기 전에는 지우지 않습니다.
3. [bootstrap.md](bootstrap.md) 1단계(옛 `bm-node` 기기 삭제, 호스트 키 정리)와 2~4단계(부트스트랩, Tailscale SSH 확인, `default-allow-ssh` 삭제)를 합니다.
4. 배포 전에 `make status`의 이미지와 `compose.yaml`의 `image:`를 비교합니다(위의 이미지 점검). 그다음 `make deploy`, `make restore BACKUP=<절대 경로>`를 합니다.
5. Exposure audit을 다시 합니다(방화벽을 새로 만들었으므로).
6. Incident log와 점검 기록에 행을 추가합니다.

## Exposure audit

`make verify`/`make probe`는 VM 쪽에서 확인할 수 있는 것만 자동으로 검사합니다: `127.0.0.1` 바인딩, Serve가 tailnet 전용인지(Funnel off), 공인 IP의 22·80·443·8737 차단. 나머지 두 가지는 VM에서 읽을 수 없으므로, 배포 직후와 방화벽·정책을 바꾼 뒤(VM 재구축 포함)에 손으로 점검하고 결과를 Incident log 아래 "점검 기록"에 남깁니다.

1. 방화벽 규칙 중 **VPC 밖의 소스를 허용하는 인바운드 규칙이 0개인지** 확인합니다. `default-allow-internal`의 `10.128.0.0/9`만 남아야 합니다.

   ```bash
   gcloud compute firewall-rules list --configuration=bm-personal --format='table(name,direction,disabled,sourceRanges.list(),allowed[].map().firewall_rule().list())'
   ```

   `direction`이 `INGRESS`, `disabled`가 `False`이면서 소스가 `10.128.0.0/9`가 아닌 행이 없어야 합니다(`default-allow-ssh`는 부트스트랩이 끝나면 지워져 있어야 함). **Assumption:** 기본 `default` 네트워크 하나만 쓰는 프로젝트입니다.
2. Tailscale admin console → Access controls의 정책 `nodeAttrs`에 **`"funnel"`이 없는지** 확인합니다.

스크립트가 `Funnel is on for this node`라고 하면 먼저 정책의 `funnel` 속성을 지워 Funnel을 끄고, VM의 Serve 상태를 확인합니다(`ssh ubuntu@bm-node sudo tailscale serve status`). 그다음 Serve를 다시 설정합니다. **Assumption (계획 05에서 확인):** 부트스트랩 뒤에는 22번이 닫혀 있으므로 `make vm-bootstrap HOST=bm-node`를 Tailscale SSH로 실행해 Serve를 다시 설정합니다. 이 명령은 VM을 바꾸므로 사용자의 OK가 필요합니다. 또한 **Assumption (계획 05에서 확인):** `serve --bg`가 443의 Funnel 플래그는 지우지만 다른 포트의 것은 지우지 않을 수 있습니다. 그 경우 `ssh ubuntu@bm-node sudo tailscale serve reset`을 사용자 OK 후에 실행합니다.

## 비용 점검

GCP 무료 등급에서 과금이 생기지 않는지 확인합니다. 외부 IPv4 요금($0.005/h, 약 $3.65/월)이 무료 등급에 포함되는지는 **Open question**입니다.

- 배포 **다음 날**과 **매월 초**에 청구 보고서를 SKU별로 봅니다: Cloud Console → Billing → Reports에서 프로젝트로 필터링하고 Group by를 SKU로 둡니다(**Assumption:** 메뉴 이름은 바뀔 수 있고, 보고서에는 하루쯤 지연이 있음).
- e2-micro 인스턴스, standard persistent disk, 외부 IP, 네트워크(아웃바운드) SKU의 금액이 모두 0이어야 합니다. Budget 알림(월 $1)이 오면 같은 보고서를 확인합니다.

- 무료 아웃바운드는 월 1GB(북미 → 전 세계, 중국·호주 제외)입니다. Tailscale DERP 중계 트래픽도 포함되므로 같은 보고서로 확인합니다.
````

````markdown
- 무료 등급 조건: e2-micro 1대, 30GB 표준 영구 디스크, 월 1GB 아웃바운드(**Verified**, 2026-10-12). Spot VM과 balanced 디스크는 무료가 아닙니다.
- 정지 후 시작하면 외부 IP가 바뀝니다. `.env`의 `BM_VM_PUBLIC_IP`를 갱신해야 `verify`가 맞는 IP를 검사합니다.
````

```markdown
# Diagnose Basic Memory

Read-only. Run only `make probe`, `make status` and `make logs` (plus `tailscale status` and `ssh ubuntu@bm-node true` on this machine). On the VM read only with `ls`, `df` and this one named file: `/opt/basic-memory/compose.yaml` (the deployed compose file). Never read the VM's `/opt/basic-memory/.env` and never run an unrestricted `cat`. Anything that writes notes, starts or restarts something, or changes settings (`make verify`, `make local-up`, `make deploy`, `make restore`, `make backup`) is a proposal for the user, not a step you run. The local `.env` belongs to the user and lives in the main checkout: do not read it by any means; ask the user to check values in it. The make targets read it from there even when you run them in a worktree.

Work top-down and stop at the first layer that fails:

1. Tailnet: `tailscale status | grep bm-node` on this machine. Missing or offline: the VM is stopped, deleted or logged out. Ask the user to check the instance (`gcloud compute instances describe <instance> --zone=us-west1-b --configuration=bm-personal --format='value(status)'`, which the user runs). `TERMINATED` means stopped: the user starts it and updates `BM_VM_PUBLIC_IP` (docs/runbooks/operations.md, "정지된 VM"); do not rebuild. Deleted or unusable means `bm-recover`.
2. SSH: `ssh ubuntu@bm-node true`. Failing while the tailnet is fine: check the Tailscale policy `ssh` rule for `tag:bm-server` (docs/runbooks/accounts.md). After a rebuilt VM, "Host key verification failed" means the user must run `ssh-keygen -R bm-node` and accept the new key (see `bm-recover`).
3. Container: `make status`. Not `(healthy)`: run `make logs` and quote the first error.
4. Memory: `make status` prints the memory and swap use. A warning containing `no active swap` means the swap file is missing: the user reruns `make vm-bootstrap` (docs/runbooks/bootstrap.md). Sustained swap use or container restarts in `make logs` mean memory pressure on the 1 GB VM: report the numbers and point to docs/decisions/0002-vm-sizing.md; do not change anything.
5. Serve: `make status` ends with `tailscale serve status`; it must show `proxy http://127.0.0.1:8737`. If it dies with "tailscale serve is not configured", Serve is missing: the user reruns bootstrap (`bm-recover` explains the Serve reset).
6. MCP: `make probe` (initialize and tools/list only; writes nothing) and read the failing step:
   - `initialize: request to <url> failed`: DNS or HTTPS; check MagicDNS and HTTPS certificates in the Tailscale admin console.
   - `initialize: HTTP 4xx`: Host header or path; propose comparing against a local container (`make local-up local-verify` starts a container and writes a test note, so the user decides).
   - `tools/list: missing tool`: the image changed; see `bm-upgrade`.
   - `Funnel is on for this node` or `accepts connections on port N`: exposure problem; point the user to "Exposure audit" in docs/runbooks/operations.md. Do not try to fix it yourself.
   - `BM_VM_PUBLIC_IP must be ...`: the user must correct `.env`. After a stop and start the external IP changes, so the value may simply be stale.
   - Probe passes but agents cannot write: check data permissions (`ssh ubuntu@bm-node ls -ln /srv/basic-memory`, owner must be 1000) and disk space (`ssh ubuntu@bm-node df -h /srv`), then propose `make verify`, which writes and deletes a test note, for the user to approve.
   - The log line `initialized (no session id)` means the server sent no session header; `initialized (session abcd****)` is a masked real id. Never print a full session id.
7. Report the failing layer, the evidence (command and output excerpt) and the proposed fix. If the incident was real, suggest a row in "Incident log" in docs/runbooks/operations.md.
```

```bash
# fstab_has_entry FSTAB -> succeeds when FSTAB already lists $SWAP_FILE as its first field.
fstab_has_entry() {
  [[ -f "$1" ]] && awk -v file="$SWAP_FILE" '$1 == file { found = 1 } END { exit !found }' "$1"
}

# ensure_swap -> a 1 GB swap file unless the VM already has active swap. Every step is safe to repeat: fallocate
# resizes a leftover file, mkswap rewrites it, and the fstab line is added once, after swapon succeeded.
ensure_swap() {
  local active fstab="$ETC_DIR/fstab"
  active="$(swapon --show --noheadings)" || die "could not list swap: is swapon installed?"
  if [[ -n "$active" ]]; then
    log "swap already active; skipping"
    return 0
  fi
  fallocate -l "${SWAP_SIZE_MB}M" "$SWAP_FILE" \
    || die "could not create $SWAP_FILE: free some disk space, then rerun 'make vm-bootstrap'"
  chmod "$SWAP_FILE_MODE" "$SWAP_FILE"
  mkswap "$SWAP_FILE" >/dev/null || die "mkswap failed on $SWAP_FILE: rerun 'make vm-bootstrap'"
  swapon "$SWAP_FILE" || die "swapon failed on $SWAP_FILE: rerun 'make vm-bootstrap'"
  if ! fstab_has_entry "$fstab"; then
    printf '%s none swap sw 0 0\n' "$SWAP_FILE" >>"$fstab"
  fi
  log "swap enabled: $SWAP_FILE (${SWAP_SIZE_MB} MB)"
}
```

```bash
#!/usr/bin/env bash
# Show VM container state, memory and swap use, and tailscale serve config.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
# shellcheck source=lib/common.sh
. "$SCRIPT_DIR/lib/common.sh"

# memory_swap_summary -> "<memory used %> <swap used MB> <swap total MB>" from one `free -m` run on the VM.
# Memory used is total minus available. Exits 1 when free prints no Mem: or no Swap: line, or a zero memory total.
memory_swap_summary() {
  remote "free -m" | awk '/^Mem:/ { if ($2 > 0) mem = int(($2 - $7) * 100 / $2) } /^Swap:/ { swap_total = $2; swap_used = $3 } END { if (mem == "" || swap_total == "") exit 1; printf "%d %d %d\n", mem, swap_used, swap_total }'
}

main() {
  local summary used swap_used swap_total
  require_cmd ssh
  require_env BM_VM_HOST BM_VM_USER

  step "containers"
  remote_compose "ps" || die "could not query containers on $BM_VM_HOST (try: ssh $BM_VM_USER@$BM_VM_HOST true)"

  step "memory and swap"
  summary="$(memory_swap_summary)" || die "could not read memory usage on $BM_VM_HOST (try: ssh $BM_VM_USER@$BM_VM_HOST free -m)"
  read -r used swap_used swap_total <<<"$summary"
  log "memory used: ${used}%"
  log "swap used: ${swap_used}/${swap_total} MB"
  if ((swap_total == 0)); then
    log "WARNING: no active swap on this 1GB VM; it can run out of memory: rerun 'make vm-bootstrap' (docs/runbooks/bootstrap.md)"
  fi

  step "tailscale serve"
  remote "sudo -n tailscale serve status" \
    || die "tailscale serve is not configured: rerun 'make vm-bootstrap HOST=<public-ip>' (docs/runbooks/bootstrap.md)"
}

main "$@"
```

Expected: PASS.
