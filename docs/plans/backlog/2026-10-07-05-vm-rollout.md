# 05 VM Rollout Plan

> **For agentic workers:** 이 계획은 사용자 계정과 클라우드 자원을 다룬다. 서브에이전트에 맡기지 말고 사용자와 같은 세션에서 진행하며(superpowers:executing-plans), 각 단계 전에 사용자 확인을 받는다. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 계획 01~04의 결과물로 실제 OCI VM을 구축하고, 스펙 §1의 완료 조건 1~4를 증거와 함께 충족한다.

**Architecture:** 사용자는 콘솔 작업(계정, 정책, VM 생성, 보안 규칙)을 하고, 에이전트는 Make 타깃 실행과 결과 기록을 맡는다. 새 코드는 없다. 문제가 생기면 `bm-diagnose` 스킬로 원인을 찾고, 코드 수정이 필요하면 별도 계획으로 분리한다.

**Tech Stack:** OCI Always Free(A1.Flex), Tailscale(Serve, SSH), 계획 01~04의 Make 타깃과 런북

**Spec:** `docs/specs/2026-10-07-basic-memory-oci-tailscale-design.md`

**Sequence:** 계획 5/5. 전제: 계획 04 완료·병합(테스트 115개, 런북과 스킬 준비됨).

## Global Constraints

- 에이전트는 사용자 대신 OCI·Tailscale 콘솔 작업을 하지 않는다. VM을 바꾸는 Make 타깃(`vm-bootstrap`, `deploy`, `restore`)은 사용자 확인 뒤에만 실행한다.
- Tailscale 인증 키는 사용자가 프롬프트에 직접 붙여 넣는다. 키를 대화, 파일, 명령 인자에 남기지 않는다.
- Git (`docs/specs/2026-10-07-git-review-policy-design.md`):
  - 이 계획은 `plan/05-vm-rollout` 브랜치의 전용 worktree에서 진행한다. `main`에 직접 커밋하지 않고, force-push·히스토리 재작성·`git gc`를 하지 않는다.
  - 커밋 형식은 `<type>: <description>`(feat, fix, refactor, docs, test, chore)이고, 메시지 끝에 트레일러 `Assisted-by: <도구> <모델>`, `Plan: 05`, `Task: N`을 단다. 커밋 명령의 `Assisted-by` 값은 시작 단계에서 정한 신원을 그대로 적는다(셸 변수는 명령 사이에 남지 않을 수 있다).
  - `Co-authored-by`와 `Signed-off-by`는 넣지 않는다(사용자 전역 설정과 저장소 정책).
- 결과는 이 계획의 Progress log와 ADR 0002에 `Verified` / `Command` 표기로 기록한다. 공인 IP와 tailnet 이름은 기록하지 않는다(`<공인 IP>`, `<tailnet>`으로 가린다).

## Review Focus

1. **22번 포트를 먼저 지워 접속 불가:** Tailscale SSH 확인 전에 22번 규칙을 지우면 시리얼 콘솔 말고는 들어갈 방법이 없다. 또 정책에 `tag:bm-server`용 `ssh` 규칙이 없으면 Tailscale SSH가 거부된다. → Step 4의 순서를 지키고, Step 1에서 정책을 함께 검토한다.
2. **재부팅 후 자동 복구:** 컨테이너(`restart: unless-stopped`)와 Serve 설정(`--bg`)이 재부팅 뒤 자동으로 돌아와야 한다. → Step 7에서 확인한다.
3. **유휴 회수:** 메모리 사용률이 20% 미만이면 7일 뒤 회수될 수 있다. → Step 8에서 24시간 뒤 측정하고 ADR 0002를 확정한다.
4. **자동 검증이 못 보는 노출:** OCI 인바운드 규칙과 tailnet 정책의 funnel 속성은 `make verify`가 읽을 수 없다. → Step 5b의 수동 점검을 거쳐야 완료 조건 2를 만족한다.
5. **복원이 기존 데이터를 되살리는지:** 새 노트 왕복만으로는 증명되지 않는다. → Step 6에서 기준 파일과 백업 이후 변경으로 직접 확인한다.

### Task 1: VM 실제 배포 (사용자와 함께, 수동 E2E)

**Files:**
- Modify: `.env`(로컬 전용, 커밋하지 않음)
- Modify: `docs/decisions/0002-vm-sizing.md`, 이 계획 파일의 Progress log, 스펙의 Open question 해소 내용
- Move: 이 계획 → `docs/plans/completed/`

**Interfaces:**
- Consumes: 런북 4개, 모든 VM 타깃
- Produces: 스펙 §1 완료 조건 1~4의 증거

이 Task는 사용자 계정과 클라우드 자원을 다룹니다. **각 단계 전에 사용자 확인을 받습니다.** 에이전트는 사용자 대신 콘솔 작업을 하지 않습니다.

- [ ] **Step 1 (사용자):** `docs/runbooks/accounts.md` 1~4단계를 완료한다. 에이전트는 정책 JSON 편집을 함께 검토한다.
- [ ] **Step 2 (사용자):** `docs/runbooks/oci-vm.md`대로 VM을 만들고, `.env`에 `BM_TAILNET_DOMAIN`과 `BM_VM_PUBLIC_IP`를 채운다.
- [ ] **Step 3 (사용자 확인 후 실행):** 인증 키를 발급한 뒤 `make vm-bootstrap HOST=<공인 IP>`를 실행한다. 사용자가 프롬프트에 키를 붙여 넣는다.
  Expected: `[bootstrap] done`과 Next steps 안내.
  **Assumption 확인:** `tailscale set --hostname --ssh`가 동작하는지 같은 명령을 한 번 더 실행해 본다(멱등성 확인). 두 번째 실행은 키 없이 `already on the tailnet`으로 끝나야 한다.
- [ ] **Step 4:** `ssh ubuntu@bm-node true` 성공을 확인한다. → (사용자) OCI 22번 인바운드 규칙을 삭제한다.
- [ ] **Step 5 (사용자 확인 후):** `make deploy verify status`
  Expected: `OK: MCP round trip passed`, `listens on 127.0.0.1 only`, `tailscale serve is tailnet only`, `refuses ports 22 80 443 8737`.
  **Assumption 확인:** 실제 `tailscale serve status` 출력에 `tailnet only` 문구가 있는지 본다. 문구가 다르면 `verify-vm.sh`의 검사와 tailscale stub을 실제 출력에 맞추는 수정 계획을 따로 만든다.
- [ ] **Step 5b (사용자, 수동 점검):** `docs/runbooks/operations.md`의 Exposure audit을 수행한다. OCI Security List(와 NSG)의 인바운드 규칙이 0개인지, tailnet 정책 `nodeAttrs`에 `funnel`이 없는지 확인하고 "점검 기록" 표에 남긴다.
  Expected: Step 5와 Step 5b를 함께 통과해야 완료 조건 2를 충족한다.
- [ ] **Step 6: 백업·복원이 기존 데이터를 되살리는지 확인 (사용자 확인 후)**
  1. 기준 파일 만들기: `ssh ubuntu@bm-node 'D=/srv/basic-memory/knowledge/basic-memory/restore-check; sudo -n -u "#1000" mkdir -p $D && date -u "+baseline %s" | sudo -n -u "#1000" tee $D/baseline.md'` → 출력 내용을 기록한다.
  2. `make backup` → 아카이브 이름을 기록하고, manifest에 기준 파일이 있는지 본다: `grep restore-check/baseline.md backups/<파일>.manifest`
  3. 백업 이후 변경 만들기: `ssh ubuntu@bm-node 'D=/srv/basic-memory/knowledge/basic-memory/restore-check; echo changed | sudo -n -u "#1000" tee -a $D/baseline.md; echo new | sudo -n -u "#1000" tee $D/after-backup.md'`
  4. `make restore BACKUP=backups/<파일>` (사용자가 `yes` 입력). restore가 manifest 대조와 verify까지 실행한다.
  5. 확인: `ssh ubuntu@bm-node 'D=/srv/basic-memory/knowledge/basic-memory/restore-check; cat $D/baseline.md; ls $D'`
  Expected: `baseline.md`의 내용이 1단계와 같고(`changed` 줄 없음), `after-backup.md`는 없다. 완료 조건 3 충족.
  6. `restore-check/` 폴더와 `/srv/basic-memory.prev-*`를 지울지 사용자에게 묻는다.
- [ ] **Step 7 (사용자 확인 후):** `ssh ubuntu@bm-node sudo reboot` → 2분 대기 → `make verify status`
  Expected: 재부팅 뒤에도 통과한다(Review Focus 2).
- [ ] **Step 8:** 24시간 뒤 `make status`의 메모리 사용률을 측정한다. ADR 0002의 재평가 기준대로 크기를 유지하거나 조정하고, Verified로 기록한 뒤 상태를 Accepted로 바꾼다.
- [ ] **Step 9:** 스펙 §3의 Open question 중 해소된 것을 Verified로 바꾼다. Progress log에 Step 3~8의 증거를 기록한다.
