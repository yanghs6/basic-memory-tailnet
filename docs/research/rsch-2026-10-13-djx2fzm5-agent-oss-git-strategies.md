# 에이전트가 커밋하고, 사람이 병합을 지킨다

- 2026-10-13 시점의 스냅샷이다. 이후 바뀐 사실은 반영하지 않는다.
- 기준 커밋: 마지막 절의 `AGENTS.md:NN` 같은 줄 번호는 `main` 5561329 기준이다.
- 표기: 출처 링크가 붙은 문장은 `Verified`(1차 출처)다. "(2차 보도)"·"(보도)"는 `Reported`, "(추론)"은 `Assumption`에 해당한다.
- 방법: 로그인 없이 공개 데이터(GitHub 웹·raw 파일·공개 API·커밋 표본)만 썼다. 에이전트 비중 수치는 표본 기반의 하한값이다.

2026-10-13 기준으로 GitHub 스타 3만 개 이상이면서 AI 코딩 에이전트를 실제 개발에 쓰는 프로젝트 약 60곳을 조사했다. 대상은 에이전트 프레임워크 20곳, 코딩 에이전트 도구 10곳, 개발 도구·런타임 20여 곳, AI 기여 정책을 둔 대형 커뮤니티 프로젝트 20곳이다. 이들의 git 전략은 에이전트 도입 전과 같은 뼈대로 수렴한다. **기본 브랜치 하나에 짧은 토픽 브랜치를 붙이는 트렁크 기반 개발, squash 병합, 사람 1명 이상의 승인, 봇이 강제하는 "승인된 이슈 먼저" 게이트**다. squash는 GitHub PR 기반 프로젝트 대부분에서 최근 커밋 20~200개 전체에 해당했다. 에이전트가 바꾼 것은 뼈대가 아니라 주변부다. `copilot/`·`claude/`·`codex/` 같은 에이전트 브랜치 접두어는 도구 기본값 그대로 남는다. 에이전트 PR은 사람 PR과 같은 승인 규칙을 통과하고, 봇이 사람 없이 에이전트의 기능 PR을 병합하게 둔 프로젝트는 찾지 못했다. 크게 갈리는 지점은 AI 표기다. Claude Code 기본값 덕분에 `Co-authored-by: <모델>` 트레일러가 사실상 표준이 됐다. 반면 Linux·Node.js·Mastodon은 `Assisted-by:`를 요구하고, Kubernetes·Rust·langchain·next.js·playwright는 AI 트레일러를 금지하고 PR 본문 공개로 대신한다. 에이전트 사용 강도는 bun처럼 2026-07 이후 생성 PR의 85.5%를 봇이 연 곳부터 봇 PR이 1~2%에 그치는 곳까지 넓다. 대부분의 에이전트 작업은 봇 계정이 아니라 사람 명의 PR 속 트레일러로 드러난다. GitHub의 병합 PR이 월 9천만 건을 넘으면서 리뷰가 병목이 됐다. 그래서 2026년의 규칙은 "어떻게 병합하나"보다 "누가 PR을 열 수 있나"로 옮겨 갔다. worktree는 도구(Claude Code, Codex 앱, Cursor)와 저장소 설정 파일(`.worktreeinclude`, pnpm `git wt`)로 퍼졌다. 다만 "에이전트 하나당 worktree 하나"를 규칙으로 적은 3만+ 저장소는 찾지 못했다.

## 에이전트 흔적은 봇 PR보다 사람 PR 속 트레일러에 더 많이 남는다

조사는 2026-10-13에 로그인 없이 공개 데이터만으로 했다. 스타 수와 기본 브랜치는 GitHub 검색 API로, 병합 방식과 트레일러는 기본 브랜치의 최근 커밋 표본으로 확인했다. 커밋 표본은 Atom 피드 20개, bare clone의 first-parent 200개, REST API 40개다. 리뷰 규칙은 공개 rulesets API(`/repos/<repo>/rules/branches/<branch>`)와 저장소 파일로 봤다. 한계도 분명하다. classic branch protection은 로그인 없이 보이지 않으므로 필수 승인 수는 ruleset을 쓰는 저장소에서만 확인됐다. 트레일러 수는 며칠~몇 주 분량의 표본이다. 사람 이름 브랜치로 올라간 에이전트 작업은 브랜치 접두어 집계에 잡히지 않는다. 스타는 3만 이상이지만 에이전트 흔적이 없는 프로젝트는 제외했다. open-webui(155k)는 지침 파일이 없고 PR 11,863개 중 Copilot 에이전트 PR이 1개뿐이었다 ([open-webui PR 검색](https://github.com/open-webui/open-webui/pulls?q=is%3Apr+author%3Aapp%2Fcopilot-swe-agent)). MetaGPT는 휴면 상태라 뺐다.

지침 파일은 사실상 표준이 됐다. AGENTS.md는 2025년 8월 OpenAI가 공개했다. 2025-12-09에는 Linux Foundation 산하 Agentic AI Foundation이 MCP·goose와 함께 이를 넘겨받았고, 지금 **6만 개 이상의 오픈소스 프로젝트**가 쓴다 ([Linux Foundation 보도자료](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). Claude Code는 CLAUDE.md가 있으면 AGENTS.md를 읽지 않는다(v2.1.277+) ([Claude Code memory 문서](https://code.claude.com/docs/en/memory)). 그래서 대형 저장소는 **AGENTS.md 하나를 정본으로 두고 CLAUDE.md·GEMINI.md를 `@AGENTS.md` 한 줄 파일이나 심볼릭 링크로 만드는** 패턴에 수렴했다. n8n, AutoGPT, goose, deer-flow, supabase, ruff, tldraw가 `@AGENTS.md` 한 줄 파일을 쓴다 ([n8n AGENTS.md](https://github.com/n8n-io/n8n/blob/master/AGENTS.md)). transformers는 두 파일 모두 `.ai/AGENTS.md`를 가리키는 심볼릭 링크다 ([transformers .ai/AGENTS.md](https://github.com/huggingface/transformers/blob/main/.ai/AGENTS.md)). zed는 세 파일 모두 `.rules`를 가리킨다 ([zed .rules](https://github.com/zed-industries/zed/blob/main/.rules)).

에이전트 사용 강도는 폭이 넓다. 가장 극단은 bun이다. 2026-07-01 이후 생성된 PR 10,236개 중 **8,752개(85.5%)를 `robobun`이 열었다**. 병합된 2,325개 중 95%는 `farm/`·`claude/`·`robobun/` 브랜치에서 왔다 ([bun PR 검색](https://github.com/oven-sh/bun/pulls?q=is%3Apr+created%3A%3E%3D2026-07-01+author%3Arobobun)). next.js는 같은 기간 병합 PR의 **19.8%가 `codex/` 브랜치**였다 ([next.js PR 검색](https://github.com/vercel/next.js/pulls?q=is%3Apr+is%3Amerged+created%3A%3E%3D2026-07-01+head%3Acodex%2F)). electron은 최근 커밋 20개 중 17개에 Claude 공동 저자 트레일러가 있다 ([electron 커밋](https://github.com/electron/electron/commits/main)). codex 저장소에는 2025-09부터 2026-06까지 `Co-authored-by: Codex` 커밋이 350개 있다 ([codex 커밋](https://github.com/openai/codex/commits/main)). Codex 팀은 앱 코드의 90% 이상을 Codex가 생성했다고 추정했다(2차 보도) ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-codex-is-built)). aider는 릴리스마다 "Aider wrote N%"를 기록하는데, v0.82.0은 92%, v0.86.0은 88%였다 ([aider HISTORY.md](https://github.com/Aider-AI/aider/blob/main/HISTORY.md)).

그런데 AI 프레임워크 대부분에서 에이전트 봇 계정이 연 PR은 병합 PR의 1~2%에 그친다. OpenHands의 `openhands-agent`가 연 병합 PR은 전체 8,005개 중 71개(약 0.9%)다 ([OpenHands PR 검색](https://github.com/OpenHands/OpenHands/pulls?q=is%3Apr+is%3Amerged+author%3Aopenhands-agent)). 반면 같은 저장소들의 squash 커밋에는 모델 이름이 박힌 트레일러가 빽빽하다. lobehub의 최근 20커밋에는 Claude Opus 5.5 트레일러만 79개가 있다 ([lobehub 커밋](https://github.com/lobehub/lobehub/commits/canary)). 지배적 패턴은 **사람이 소유한 PR 안에 에이전트가 쓴 커밋**이고, 봇 PR 비율은 실제 에이전트 사용량을 잘 보여 주지 못한다. 외부 에이전트 기여를 제한하는 프로젝트도 유지보수자 자신은 에이전트를 쓴다. Node.js는 최근 40커밋 중 24개에 `Assisted-by:`가 있고, 그중 20개가 James M Snell의 `Assisted-by: OpenCode`다 ([Node.js 커밋 표본](https://api.github.com/repos/nodejs/node/commits?per_page=40)). Home Assistant는 40커밋 중 19개에 AI 공동 저자 트레일러가 있다 ([Home Assistant 커밋 표본](https://api.github.com/repos/home-assistant/core/commits?per_page=40)). Ghostty는 외부 기여자에게 모든 AI 사용 공개를 요구하면서도 프로젝트 자체가 "상당한 AI 도움으로 작성됐다"고 밝힌다 ([Ghostty AI_POLICY.md](https://raw.githubusercontent.com/ghostty-org/ghostty/main/AI_POLICY.md)).

## 트렁크와 squash가 표준이고, 예외는 병합 봇과 통합 브랜치뿐이다

조사한 저장소는 거의 모두 트렁크 기반이다. 기본 브랜치 하나(`main`/`master`)에 짧게 사는 토픽 브랜치를 PR로 붙이고, 태그는 매일에서 매주 사이로 찍으며, 장기 브랜치는 유지보수 릴리스용으로만 둔다. 예외는 기본 브랜치 앞에 통합 브랜치를 두는 경우다. lobehub는 `canary`(클라우드 프로덕션)에서 개발하고, `main`(릴리스)은 canary에서 주기적으로 cherry-pick 받는다 ([lobehub AGENTS.md](https://github.com/lobehub/lobehub/blob/canary/AGENTS.md)). AutoGPT는 기본 브랜치가 `master`다. 하지만 워크플로가 `dev`나 `hotfix/*`에서 오지 않은 PR의 대상을 자동으로 `dev`로 바꾼다 ([AutoGPT 워크플로](https://github.com/Significant-Gravitas/AutoGPT/blob/master/.github/workflows/repo-pr-enforce-base-branch.yml)). next.js(`canary`), opencode(`dev`), storybook(`next`), tauri(`dev`), Home Assistant(`dev`)도 이 부류다. langflow는 PR을 진행 중인 `release-X.Y.Z` RC 브랜치로 받는다 ([langflow CONTRIBUTING](https://github.com/langflow-ai/langflow/blob/main/CONTRIBUTING.md)). 릴리스 자동화도 흔하다. OpenHands는 release-please를 쓰고, 에이전트에게 "release-please 브랜치를 손으로 고치지 말라"고 적었다 ([OpenHands AGENTS.md](https://github.com/OpenHands/OpenHands/blob/main/AGENTS.md)). gemini-cli는 nightly·preview·stable마다 `release/` 브랜치를 만들어 414개가 쌓였고, 매주 화요일 stable과 preview를 자른다 ([gemini-cli releases.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/releases.md)). goose는 버전 bump PR 병합, `release/<version>` 자동 생성, cherry-pick, 태그 순서를 문서로 정했다 ([goose RELEASE.md](https://github.com/aaif-goose/goose/blob/main/RELEASE.md)).

브랜치 이름에서는 에이전트가 가장 잘 보인다. 대부분 도구 기본 접두어가 그대로 남는다. codex는 브랜치 4,701개 중 **1,057개가 `codex/`**다. vscode는 `copilot/` 1,453개와 UUID 이름의 `agents/` 254개가 있다 ([vscode 브랜치](https://github.com/microsoft/vscode/branches)). bun은 12,873개 중 `farm/` 5,958개, `robobun/` 2,817개, `claude/` 2,455개다 ([bun 브랜치](https://github.com/oven-sh/bun/branches)). Copilot 클라우드 에이전트는 플랫폼 차원에서 `copilot/` 브랜치 하나에만 푸시할 수 있어 접두어가 보장된다 ([GitHub Copilot 위험과 완화](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). 접두어를 규칙으로 정한 곳은 드물다. bun만 CI 때문에 브랜치가 `claude/`로 시작해야 한다고 의무화했다 ([bun CLAUDE.md](https://github.com/oven-sh/bun/blob/main/CLAUDE.md)). opencode는 반대로 슬래시와 `feat/`·`fix/` 같은 접두어를 금지하고, 세 단어 이하의 하이픈 이름을 요구한다 ([opencode AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/AGENTS.md)). 사람 쪽 규칙은 작업 추적과 묶인다. langchain은 `<github-username>/<scope>/<short-description>`을 쓴다 ([langchain AGENTS.md](https://github.com/langchain-ai/langchain/blob/master/AGENTS.md)). n8n은 Linear가 제안한 티켓 이름을 쓰되 보안 수정은 예외로 둔다 ([n8n AGENTS.md](https://github.com/n8n-io/n8n/blob/master/AGENTS.md)). crewAI는 `<type>/<short-description>`, playwright는 `fix-<issue-number>`다. 브랜치 정리 규칙은 거의 없어 수천 개의 에이전트 브랜치가 원격에 남아 있다. 예외는 bun 정도로, 90일 넘게 멈춘 robobun PR을 매일 자동으로 닫는다 ([bun close-stale 워크플로](https://github.com/oven-sh/bun/blob/main/.github/workflows/close-stale-robobun-prs.yml)).

병합 방식은 squash가 압도적이다. AI 프레임워크 20곳 중 14곳은 최근 20커밋이 전부 `(#N)`으로 끝나는 squash였다. gemini-cli·OpenHands·goose는 최근 200커밋이 전부 squash였고, 개발 도구 핵심 16곳은 최근 20커밋에 merge commit이 하나도 없었다 ([vllm 커밋](https://github.com/vllm-project/vllm/commits/main)). 여러 곳은 이를 ruleset으로 강제한다. codex·opencode·OpenHands·cline은 squash 전용이다. next.js·electron·uv는 linear history를 요구한다. gemini-cli와 zed는 squash 방식의 merge queue를 쓴다 ([codex rules](https://api.github.com/repos/openai/codex/rules/branches/main), [zed rules](https://api.github.com/repos/zed-industries/zed/rules/branches/main)). langchain은 "squash 전용 정책"을 워크플로 주석에 적었다. fork의 `master`에서 온 PR이 2-parent merge commit으로 들어오지 못하게 막는 워크플로도 따로 뒀다 ([langchain block_fork_main_prs.yml](https://github.com/langchain-ai/langchain/blob/master/.github/workflows/block_fork_main_prs.yml)). 에이전트 작업에 squash가 잘 맞는 이유는 세 가지로 보인다(추론). PR 하나가 커밋 하나가 되고, Conventional Commit 형식의 PR 제목이 그대로 커밋 제목이 되며, 에이전트의 잡다한 WIP 커밋이 사라진다. deno는 "PR이 병합될 때 모든 커밋이 squash된다"며 force push를 금지한다 ([deno CLAUDE.md](https://github.com/denoland/deno/blob/main/CLAUDE.md)).

예외는 네 부류다. 첫째, 병합 봇이나 릴리스 담당자가 merge commit을 만드는 곳이다. Kubernetes는 Prow를 쓰고 최근 40커밋 중 24개가 merge commit이다. Rust는 bors의 "Auto merge"·"Rollup merge" 커밋이 23/40이다. Godot는 릴리스 매니저가 몇 초 간격으로 일괄 병합한 커밋이 25/40이다. moby와 storybook도 merge commit을 쓴다 ([Kubernetes PR 절차](https://www.kubernetes.dev/docs/guide/pull-requests/), [moby 커밋](https://github.com/moby/moby/commits/master)). 둘째, Linux와 git은 메일링 리스트로 개발하고 GitHub는 미러일 뿐이다. Linux mainline에 병합할 수 있는 사람은 Linus Torvalds 한 명이다 ([kernel 개발 절차](https://docs.kernel.org/process/2.Process.html)). 셋째, rebase나 직접 푸시를 쓰는 곳이다. Node.js는 GitHub의 녹색 병합 버튼을 금지하고, `git node land`나 `commit-queue` 라벨로 `PR-URL:`·`Reviewed-By:` 메타데이터를 붙여 반영한다 ([Node.js collaborator guide](https://raw.githubusercontent.com/nodejs/node/main/doc/contributing/collaborator-guide.md)). curl은 유지보수자가 rebase해 푸시하고 `Closes #N`으로 PR을 닫는다. 최근 100커밋 중 merge commit은 0개다 ([curl CONTRIBUTE.md](https://raw.githubusercontent.com/curl/curl/master/docs/CONTRIBUTE.md)). pi는 최근 200커밋 중 180개가 유지보수자 직접 커밋이다 ([pi rules](https://api.github.com/repos/earendil-works/pi/rules/branches/main)). hermes-agent는 최근 20커밋 중 18개에 PR 번호가 없다. AGENTS.md에는 "오래된 브랜치를 squash하면 더 새로운 수정이 조용히 되돌려지니 병합 전에 main 위로 rebase하라"와 "작성자가 남도록 cherry-pick으로 살려라"는 규칙이 있다 ([hermes-agent AGENTS.md](https://github.com/NousResearch/hermes-agent/blob/main/AGENTS.md)). 넷째, codex는 **2026-07-10부터 공개 `main`이 내부 저장소의 단방향 export**다. 그 뒤 커밋은 모두 `copyberry` 봇이 `GitOrigin-RevId:` 트레일러를 달아 커밋한다. 그 전 11,131개 first-parent 커밋은 merge가 0개인 순수 squash였다 ([codex 커밋](https://github.com/openai/codex/commits/main)).

squash에는 AI 표기와 얽힌 부작용이 있다. GitHub squash는 PR 안 커밋들의 트레일러를 squash 커밋 본문에 모은다. 그래서 PR 하나에 에이전트 커밋이 여러 개면 트레일러가 겹겹이 쌓이고, lobehub 20커밋에 Claude 트레일러가 79개 쌓인 것도 이 때문이다. langchain은 그래서 개별 커밋이 아니라 squash될 메시지를 검사한다. next.js·tldraw가 AGENTS.md로 트레일러를 금지했는데도 main에 트레일러가 새어 들어오는 것도 같은 구조 때문으로 보인다(추론, AI 표기 절에서 다시 다룬다).

## 에이전트 PR도 사람 PR과 같은 승인 문을 지난다

호스팅 에이전트는 플랫폼 단계에서 먼저 울타리가 쳐진다. GitHub Copilot 클라우드 에이전트(구 coding agent)는 `copilot/` 브랜치 하나에만 푸시하고 초안 PR을 연다. PR을 "Ready for review"로 바꾸거나 승인·병합할 수는 없다. **작업을 시킨 사람은 그 PR을 승인할 수 없고**, Actions 워크플로는 쓰기 권한자가 "Approve and run workflows"를 누를 때까지 기본적으로 돌지 않는다 ([GitHub Copilot 위험과 완화](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). 그래서 승인 1개를 요구하는 저장소에서 Copilot PR은 사실상 요청자와 승인자, 사람 두 명을 거친다(추론). Claude Code GitHub Action도 트리거한 사용자에게 쓰기 권한이 있어야 한다. `allowed_bots`에 없는 봇은 거부해 봇끼리의 무한 루프를 막는다 ([Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)). 2026-02-04부터는 GitHub 이슈의 담당자로 Claude·Codex·Copilot을 지정할 수 있고, 이들은 기본으로 초안 PR을 만든다 ([GitHub Changelog 2026-02-04](https://github.blog/changelog/2026-02-04-claude-and-codex-are-now-available-in-public-preview-on-github/)).

저장소 규칙은 에이전트를 따로 다루지 않는다. 공개 rulesets의 전형은 **승인 1개 + code owner 리뷰**다(codex, gemini-cli, cline, vscode, next.js, electron). 여기에 규칙을 더한 곳이 있다. cline은 마지막 푸시 이후의 승인(`require_last_push_approval`)과 리뷰 스레드 해결을 요구한다 ([cline rules](https://api.github.com/repos/cline/cline/rules/branches/main)). vscode는 마지막 푸시 승인에 Copilot 코드 리뷰 규칙(`copilot_code_review`)을 더했다 ([vscode rules](https://api.github.com/repos/microsoft/vscode/rules/branches/main)). 반대쪽 끝에는 승인 0개인 opencode·uv·zed와 PR 규칙 자체가 없는 pi가 있다. zed는 code owner 리뷰와 merge queue로 이를 보완한다. 커뮤니티 프로젝트는 더 무겁다. Node.js는 작성자가 아닌 협업자 2명의 승인과 48시간 대기를 요구하고, 7일이 지나면 승인 1명으로 줄여 준다 ([Node.js collaborator guide](https://raw.githubusercontent.com/nodejs/node/main/doc/contributing/collaborator-guide.md)). Kubernetes는 OWNERS 파일 기반의 `/lgtm`·`/approve`를 쓴다. n8n은 GitHub CODEOWNERS 대신 `OWNERS` 파일과 커스텀 "Required Reviews" 커밋 상태로 팀 승인을 강제한다 ([n8n OWNERS](https://github.com/n8n-io/n8n/blob/master/OWNERS)). 조사한 어떤 저장소도 에이전트 PR에만 적용되는 별도 승인 규칙을 두지 않았다.

대신 PR이 열리기 전 단계가 두꺼워졌다. GitHub에 따르면 병합 PR은 2023년 1월 월 2,500만 건에서 2026년 중반 **월 9천만 건 이상**으로 늘었지만, PR 하나를 리뷰하는 시간은 그대로다 ([GitHub 블로그 2026-06-18](https://github.blog/open-source/maintainers/how-pull-request-limits-are-cutting-down-the-noise/)). 별 500개 이상 저장소에서 에이전트 PR의 수용률은 사람 PR(76.8%)보다 낮았다. Copilot 38.2%, Claude Code 52.5%, Codex 65.3%다 ([AIDev 논문](https://arxiv.org/html/2507.15003v1)). 다만 초안을 빼고 ready 상태 PR만 세는 PRarena에서는 Copilot 병합률이 96%여서, 수치는 초안을 포함하느냐에 크게 좌우된다 ([PRarena](https://github.com/aavetis/PRarena)). 이런 배경에서 **"승인된 이슈 먼저, PR은 그다음"을 봇이 강제**하는 방식이 표준이 됐다. OpenHands는 연결된 이슈에 `ready-for-dev` 라벨이 있어야 PR을 받는다. 이 라벨은 트리아지 자동화와 쓰기 권한자만 붙일 수 있고, 다른 사람이 붙이면 지워진다 ([OpenHands issue-readiness-check.yml](https://github.com/OpenHands/OpenHands/blob/main/.github/workflows/issue-readiness-check.yml)). langchain·langgraph는 유지보수자가 승인한 이슈에 배정된 사람만 PR을 낼 수 있다 ([langchain PR 템플릿](https://github.com/langchain-ai/langchain/blob/master/.github/PULL_REQUEST_TEMPLATE.md)). mem0는 `accepted` 라벨이 붙은 이슈와 vouch 명단이라는 두 관문을 둔다 ([mem0 AGENTS.md](https://github.com/mem0ai/mem0/blob/main/AGENTS.md)). gemini-cli는 이슈 링크 없는 PR을 자동으로 닫고, `/assign`을 3개로 제한하며, PR rate limiter를 돌린다 ([gemini-cli CONTRIBUTING](https://github.com/google-gemini/gemini-cli/blob/main/CONTRIBUTING.md)). 더 강한 곳도 있다. pi는 유지보수자가 `lgtm`을 달기 전까지 신규 기여자의 PR을 자동으로 닫는다 ([pi CONTRIBUTING](https://github.com/earendil-works/pi/blob/main/CONTRIBUTING.md)). Ghostty는 vouch 받지 않은 사람의 PR을 자동으로 닫는다 ([Ghostty CONTRIBUTING](https://raw.githubusercontent.com/ghostty-org/ghostty/main/CONTRIBUTING.md)). codex는 외부 PR을 아예 받지 않는다 ([codex contributing](https://github.com/openai/codex/blob/main/docs/contributing.md)). Ladybird와 tldraw는 외부 PR을 닫았다 ([tldraw CONTRIBUTING](https://raw.githubusercontent.com/tldraw/tldraw/main/CONTRIBUTING.md)). GitHub도 2026-02에 PR 끄기와 협업자 전용 PR 설정을 내놨다 ([GitHub Changelog 2026-02-13](https://github.blog/changelog/2026-02-13-new-repository-settings-for-configuring-pull-request-access/)). 2026-06에는 쓰기 권한이 없는 사용자별로 열린 PR 수를 제한하는 기능을 추가했다. 에이전트가 연 PR은 이 제한에 포함되고, 초안은 빠진다 ([GitHub 블로그 2026-06-18](https://github.blog/open-source/maintainers/how-pull-request-limits-are-cutting-down-the-noise/)).

에이전트 지침에서 가장 자주 보이는 PR 규칙은 초안 유지와 푸시 통제다. next.js는 에이전트에게 `gh pr ready`를 쓰지 말고 PR을 초안으로 두라고 한다 ([next.js AGENTS.md](https://github.com/vercel/next.js/blob/canary/AGENTS.md)). n8n은 `gh pr create --draft`를 지시한다. grafana는 작업 설명에 "PR을 열어라"가 있어도 그것은 의도일 뿐 리뷰 없이 푸시해도 된다는 허락이 아니라며, `git push` 전에 사람의 명시적 승인을 받게 한다 ([grafana AGENTS.md](https://github.com/grafana/grafana/blob/main/AGENTS.md)). playwright는 지시 없이는 절대 푸시하지 말라고 한다 ([playwright AGENTS.md](https://github.com/microsoft/playwright/blob/main/AGENTS.md)). Rust의 AGENTS.md는 푸시 전에 사용자가 변경을 이해하고 직접 검토했는지 확인받게 하고, **"에이전트 리뷰는 치지 않는다"**고 못 박았다 ([Rust AGENTS.md](https://raw.githubusercontent.com/rust-lang/rust/main/AGENTS.md)).

AI 리뷰는 대체로 보조 역할에 머물지만, 일부는 관문이 됐다. goose는 Codex를 AI 리뷰어로 쓰고, 기여자가 모든 지적에 수정이나 한 줄 답으로 응하지 않으면 PR을 닫을 수 있다고 했다 ([goose CONTRIBUTING](https://github.com/aaif-goose/goose/blob/main/CONTRIBUTING.md)). pnpm은 CodeRabbit이 승인한 뒤에야 유지보수자가 리뷰를 시작한다 ([pnpm PR 템플릿](https://github.com/pnpm/pnpm/blob/main/.github/pull_request_template.md)). vscode는 Copilot 코드 리뷰를 ruleset에 넣었다. 반대로 Rust는 LLM 리뷰 봇이 절대 차단 요소가 되면 안 된다고 했고, LLM 리뷰만으로 병합하거나 거절하는 것도 금지했다 ([Rust forge](https://forge.rust-lang.org/policies/llm-usage.html)). LLVM은 사람 검토 없이 글을 올리는 리뷰 봇을 금지했다 ([LLVM AIToolPolicy](https://llvm.org/docs/AIToolPolicy.html)). 병합은 끝까지 사람이 한다. 봇이 사람 없이 에이전트의 기능 PR을 병합하는 저장소는 찾지 못했다. 가장 가까운 사례는 앱이 PR을 승인하고 auto-merge를 켜는 워크플로가 있는 n8n이지만, 에이전트 PR #40926도 결국 사람 계정이 병합했다 ([n8n PR #40926](https://github.com/n8n-io/n8n/pull/40926)).

## CI는 결과를 막고, AI 전용 검사는 PR 위생과 트레일러를 막는다

필수 체크는 대개 여러 잡을 묶은 집계 체크다. codex는 `cla`와 `CI required`, uv는 `all required jobs passed`, OpenHands는 `test-and-build (ubuntu)`, gemini-cli는 `cla/google`·`CI`·`E2E (Chained)`다 ([codex blocking-ci.yml](https://github.com/openai/codex/blob/main/.github/workflows/blocking-ci.yml), [gemini-cli rules](https://api.github.com/repos/google-gemini/gemini-cli/rules/branches/main)). 여기에 Conventional Commits 형식의 PR 제목 검사가 붙는다(langchain은 scope 필수, opencode·deno·dify·n8n·vllm·crewAI도 검사). electron은 릴리스 노트, semver 라벨, PR 제목, backport 라벨까지 필수 체크 8개를 둔다 ([electron rules](https://api.github.com/repos/electron/electron/rules/branches/main)). 조사한 프로젝트들은 누가 썼는지가 아니라 테스트·타입 검사·CLA 같은 결과로 CI를 막는다.

merge queue는 예상보다 널리 쓰인다. 워크플로에 `merge_group` 트리거가 있는 저장소는 n8n, dify, langchain, transformers, langflow, AutoGPT, goose, autogen(.NET 쪽만)이다 ([n8n 워크플로](https://github.com/n8n-io/n8n/tree/master/.github/workflows)). ruleset으로 설정까지 확인된 곳은 둘이다. gemini-cli는 ALLGREEN, 한 번에 2~5개, 응답 대기 60분이고, zed는 SQUASH, ALLGREEN, 최대 7개 빌드다 ([gemini-cli rules](https://api.github.com/repos/google-gemini/gemini-cli/rules/branches/main), [zed rules](https://api.github.com/repos/zed-industries/zed/rules/branches/main)). GitHub merge queue 대신 다른 장치를 쓰는 곳도 있다. vllm은 `ready`·`verified` 라벨 기반의 Mergify를 쓴다 ([vllm mergify.yml](https://github.com/vllm-project/vllm/blob/main/.github/mergify.yml)). Rust는 bors rollup, Node.js는 `commit-queue` 라벨, Kubernetes는 Prow를 쓴다. 서명 커밋은 bun·next.js·electron의 ruleset이 요구한다. grafana는 서명 없는 커밋과 PR은 에이전트가 쓴 것이라도 거절한다고 적었다 ([grafana CONTRIBUTING](https://github.com/grafana/grafana/blob/main/CONTRIBUTING.md)). 법적 관문은 CLA가 다수다(codex, gemini-cli, n8n, mem0, CPython, react, zed, angular 등). DCO는 vllm, Linux, git, Node.js 정도이고, vllm은 최근 20커밋 모두에 `Signed-off-by`가 있다 ([vllm DCO](https://github.com/vllm-project/vllm/blob/main/DCO)). Kubernetes는 EasyCLA가 공동 저자까지 검사하도록 켰는데, 그 이유가 **"AI는 CLA에 서명할 수 없다"**였다 ([Kubernetes dev 메일링 리스트](https://groups.google.com/a/kubernetes.io/g/dev/c/7Y9016gdFZw/m/nUUmxFPzAQAJ)).

에이전트 전용 CI 검사는 결과가 아니라 PR 위생과 출처를 본다. langchain의 `pr_lint_trailer.yml`은 squash될 메시지에서 `Co-[Aa]uthored-[Bb]y:.*<noreply@anthropic\.com>` 패턴을 찾는다. 같은 패턴의 푸시를 거부하는 org ruleset `block-anthropic-coauthor`가 짝을 이룬다 ([langchain pr_lint_trailer.yml](https://github.com/langchain-ai/langchain/blob/master/.github/workflows/pr_lint_trailer.yml)). transformers는 `peakoss/anti-slop`으로 "Code agent slop" 라벨만 붙이고, PR을 닫거나 잠그지는 않는다 ([transformers anti-slop.yml](https://github.com/huggingface/transformers/blob/main/.github/workflows/anti-slop.yml)). OpenHands는 PR 본문에 사람 전용 `HUMAN:` 섹션이 제대로 있는지 검사한다 ([OpenHands pr-description-check.yml](https://github.com/OpenHands/OpenHands/blob/main/.github/workflows/pr-description-check.yml)). lobehub는 필수 항목이 빠진 PR에 `pr:incomplete`를 붙이고 14일 뒤 닫는다 ([lobehub PR 템플릿](https://github.com/lobehub/lobehub/blob/canary/.github/PULL_REQUEST_TEMPLATE.md)). hermes-agent는 PR #25045가 두 번째 루트 커밋을 접붙인 일을 겪은 뒤, main과 공통 조상이 없는 PR을 거부하는 `history-check.yml`을 만들었다 ([hermes history-check.yml](https://github.com/NousResearch/hermes-agent/blob/main/.github/workflows/history-check.yml)). cline은 클라우드 에이전트가 PR 본문에 붙이는 홍보 배지를 지우는 워크플로를 돌린다 ([cline 워크플로](https://github.com/cline/cline/blob/main/.github/workflows/repo-strip-agent-badges.yml)). bun은 작성자가 `robobun`이거나 본문에 "🤖 Generated with"가 있으면 `claude` 라벨을 붙인다 ([bun auto-label 워크플로](https://github.com/oven-sh/bun/blob/main/.github/workflows/auto-label-claude-prs.yml)). claude-code 저장소는 Claude를 실행하는 잡이 egress 방화벽 러너나 `--permission-mode auto`를 빼면 실패하게 한다 ([claude-code CLAUDE.md](https://github.com/anthropics/claude-code/blob/main/CLAUDE.md)). 이 검사들은 모두 같은 흐름 위에 있다. AGENTS.md에 산문으로 적던 규칙을 기계가 검사하는 규칙으로 옮기는 흐름이다.

## AI 표기는 Co-authored-by, Assisted-by, 금지의 세 갈래로 갈라졌다

AI 도움을 git에 남기는 공통 표준은 없다. 프로젝트들은 아래처럼 갈린다.

| 방식 | 대표 프로젝트 | 규칙 요지 |
|---|---|---|
| 모델명 `Co-authored-by` 의무·권장 | AutoGPT, vllm, electron | AutoGPT는 커밋마다 `Co-authored-by: MODEL NAME/VERSION (AGENT PLATFORM) <email>`을 의무로 하고, 모르는 값은 `unknown`, 이메일이 없으면 `agent@example.invalid`를 쓴다 ([AutoGPT AGENTS.md](https://github.com/Significant-Gravitas/AutoGPT/blob/master/AGENTS.md)). vllm은 `Co-authored-by:`와 사람의 DCO `Signed-off-by`를 함께 쓴다 ([vllm AGENTS.md](https://github.com/vllm-project/vllm/blob/main/AGENTS.md)). electron은 `Assisted-By: Claude Opus 4.5, Claude Code`나 `Co-Authored-By: Claude <noreply@anthropic.com>`를 권장한다 ([electron AI 정책](https://github.com/electron/governance/blob/main/policy/ai.md)) |
| `Assisted-by` 의무·권장 | Linux, Node.js, Mastodon, LLVM, curl | Linux는 `Assisted-by: LLM [도구]`(2026-08 단순화)를 쓰고 AI의 `Signed-off-by`를 금지한다 ([kernel coding-assistants](https://docs.kernel.org/process/coding-assistants.html)). Node.js는 `Assisted-by: <agent name>`과 사람 `Signed-off-by`를 요구하고 에이전트 `Co-authored-by`를 금지한다. Mastodon은 `Assisted-by: Name of AI`를 쓴다 ([Mastodon AI_POLICY.md](https://raw.githubusercontent.com/mastodon/.github/main/AI_POLICY.md)) |
| 모델명 없는 일반 트레일러 | Neovim | `AI-assisted`만 허용하고, 모델·서비스 이름과 AI 저자 표기를 금지한다 ([Neovim AGENTS.md](https://raw.githubusercontent.com/neovim/neovim/master/AGENTS.md)) |
| 트레일러 금지, PR 본문 공개 | Kubernetes, Rust, langchain, next.js, tldraw, playwright, moby, Bevy | Kubernetes는 AI co-author와 `assisted-by`·`co-developed` 트레일러를 금지하고 PR에 YES/NO를 적게 한다. moby는 PR 본문 끝에 "Created with: <AGENT NAME>"을 적게 한다 ([moby AGENTS.md](https://github.com/moby/moby/blob/master/AGENTS.md)). Bevy는 커밋 저자와 `Co-authored-by`에 사람만 올 수 있다 ([Bevy AI 정책](https://bevy.org/learn/contribute/policies/ai/)) |
| PR 양식·라벨 | crewAI, dify, lobehub, mem0, OpenHands, pytorch, deer-flow | crewAI는 `llm-generated` 라벨을 요구한다 ([crewAI CONTRIBUTING](https://github.com/crewAIInc/crewAI/blob/main/.github/CONTRIBUTING.md)). dify는 `From <Tool Name>`을 쓰게 한다 ([dify PR 템플릿](https://github.com/langgenius/dify/blob/main/.github/pull_request_template.md)). mem0는 "AI 없음 / AI 보조 / AI 생성" 체크박스를 둔다 ([mem0 PR 템플릿](https://github.com/mem0ai/mem0/blob/main/.github/PULL_REQUEST_TEMPLATE.md)). 그 밖에 HUMAN/AGENT 섹션, "Agent details" 같은 양식이 있다 |
| 공개 불필요 | goose, CPython | goose는 "AI를 썼다고 알릴 필요 없다, 책임은 당신에게 있다"고 한다. CPython은 공개를 "환영하지만 필수는 아니다"라고 한다 ([CPython devguide](https://devguide.python.org/getting-started/ai-tools/index.html)) |

실제로 남는 표기는 규칙보다 도구 기본값이 정한다. Claude Code는 기본으로 `Co-Authored-By: <모델 이름> <noreply@anthropic.com>` 트레일러와 "🤖 Generated with [Claude Code]" PR 푸터를 붙인다. 클라우드 세션에서는 `Claude-Session` 트레일러도 더한다 ([Claude Code settings reference](https://code.claude.com/docs/en/settings-reference)). Copilot 커밋은 Copilot이 저자이고, 작업을 요청한 사람이 공동 저자다 ([GitHub Copilot 위험과 완화](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). aider는 작성자 이름을 "<이름> (aider)"로 바꾸고 `Co-authored-by: aider (<model>)`를 붙인다 ([aider 커밋](https://github.com/Aider-AI/aider/commits/main)). 그 결과 AI 프레임워크와 코딩 도구 표본에서 `Assisted-by`·`Generated-by` 트레일러는 0개였다. `Assisted-by`는 DCO와 메일링 리스트식 트레일러 문화가 있는 Linux·Node.js 쪽에 몰려 있다. CLA를 쓰는 Kubernetes는 반대로 트레일러를 막았는데, 근거는 두 가지다. AI는 CLA에 서명할 수 없고, `assisted-by` 트레일러가 벤더의 "Kubernetes가 우리 유료 도구를 쓰고 보증한다"는 마케팅에 쓰인다는 것이다 ([Kubernetes dev 메일링 리스트](https://groups.google.com/a/kubernetes.io/g/dev/c/7Y9016gdFZw/m/nUUmxFPzAQAJ)). langchain의 차단도 AI 사용을 숨기려는 것이 아니다. `noreply@anthropic.com`이 GitHub 공동 저자로 뜨는 출처 문제를 겨냥한 것이고, PR 본문의 AI 관여 고지는 오히려 의무다 ([langchain AGENTS.md](https://github.com/langchain-ai/langchain/blob/master/AGENTS.md)). Rust는 PR 설명이 bors 병합 커밋에 들어가므로, 공개문을 `homu-ignore` 블록으로 감싸 git 이력에서 뺄 수 있게 했다 ([Rust PR 템플릿](https://raw.githubusercontent.com/rust-lang/rust/main/.github/pull_request_template.md)). 이 문제를 다룬 DCO 프로젝트는 하나같이 **`Signed-off-by`는 사람만** 넣을 수 있다고 정했다. Linux 문서는 DCO를 법적으로 인증할 수 있는 것은 사람뿐이라고 적었다 ([kernel coding-assistants](https://docs.kernel.org/process/coding-assistants.html)).

규칙과 실제는 자주 어긋난다. next.js는 co-author 푸터를 금지했지만 최근 20커밋 중 2개에 트레일러가 있고, tldraw는 6개에 Claude 트레일러가 있다 ([tldraw 커밋](https://github.com/tldraw/tldraw/commits/main)). moby도 금지 규칙 아래에서 `Assisted-By: Claude Opus 5.5` 커밋이 하나 나왔다 ([moby 커밋](https://github.com/moby/moby/commits/master)). AGENTS.md의 금지는 그 파일을 읽는 에이전트에만 닿고, squash가 PR 커밋의 트레일러를 모으기 때문으로 보인다(추론). Linux에서는 7.2-rc4까지 `Assisted-by` 커밋이 1,200개를 넘었다. 그런데 Jakub Kicinski는 자기가 적용하는 패치에서 이 태그를 지우고, Christian Brauner는 공개가 쓸모없다고 했다. 결국 2026-08에 형식이 모델 이름 없는 `Assisted-by: LLM [도구]`로 단순화됐다(보도와 커밋 이력) ([LWN](https://lwn.net/SubscriberLink/1083275/d5518174ec4dcbcb/)). Node.js 안에서도 문서끼리 어긋난다. AGENTS.md는 에이전트 이름을 적은 `Assisted-by`를 요구하는데, ai-guidelines.md는 커밋 메시지에서 영리 AI 브랜드를 익명화하라고 한다 ([Node.js ai-guidelines.md](https://raw.githubusercontent.com/nodejs/node/main/doc/contributing/ai-guidelines.md)). 트레일러로 에이전트 비중을 재면 하한값만 나온다. codex는 export 전환 뒤 `Co-authored-by: Codex`가 0개가 됐고, Claude Code 트레일러는 설정으로 끌 수 있다. 트레일러의 성격도 "어떤 모델이 썼는지 추적하는 장치"에서 "더 꼼꼼히 리뷰하라는 신호"로 바뀌는 중으로 보인다(추론).

## 에이전트 규칙은 "시키기 전엔 커밋·푸시하지 말라"로, 병렬 실행은 worktree로 모인다

AGENTS.md에 반복되는 git 규칙은 대부분 금지 목록이다. pi가 가장 상세하다. 사용자가 요청할 때만 커밋한다. 같은 작업 디렉터리에서 여러 세션이 동시에 돌 수 있으니, 이번 세션에서 바꾼 파일만 경로를 지정해 스테이징한다. `git add -A`·`git add .`·`git reset --hard`·`git checkout .`·`git clean -fd`·`git stash`·`git commit --no-verify`와 force push는 모두 금지다 ([pi AGENTS.md](https://github.com/earendil-works/pi/blob/main/AGENTS.md)). `--no-verify` 금지는 crewAI·pnpm·turborepo에도 있다 ([pnpm AGENTS.md](https://github.com/pnpm/pnpm/blob/main/AGENTS.md)). force push 금지는 deno에도 있고, playwright는 커밋 amend까지 막았다. 그 밖의 규칙도 있다. OpenHands는 긴 커밋 메시지가 셸에서 깨지지 않게 `git commit -F <파일>`을 쓰게 한다 ([OpenHands AGENTS.md](https://github.com/OpenHands/OpenHands/blob/main/AGENTS.md)). uv·ruff는 대화·프롬프트·작업 이력을 PR 설명에 흘리지 말라고 한다 ([uv AGENTS.md](https://github.com/astral-sh/uv/blob/main/AGENTS.md)). vllm은 PR 전에 `gh pr list --search`로 중복을 확인하고, 중복이거나 사소하면 진행하지 말라고 한다("fail-closed") ([vllm AGENTS.md](https://github.com/vllm-project/vllm/blob/main/AGENTS.md)). n8n은 보안 수정의 브랜치와 커밋 이름을 중립적으로 쓰게 하고, AutoGPT는 범위 밖 변경을 PR의 20% 미만으로 제한한다.

PR 본문은 사람과 에이전트의 경계선이 됐다. OpenHands는 `HUMAN:` 섹션을 사람 전용으로 두고, 에이전트가 이 섹션을 추가·수정·이동·삭제하지 못하게 한다. `AGENT:` 섹션에는 단위 테스트가 아닌 종단 간 실행 증거를 요구한다 ([OpenHands PR 템플릿](https://github.com/OpenHands/OpenHands/blob/main/.github/pull_request_template.md)). Rust는 AI 사용 공개문을 에이전트가 쓰거나 고쳐 쓰면 안 되고 사용자가 직접 써야 한다고 정했다. 감독 없는 에이전트를 걸러 내는 덫도 나왔다. Ghostty AGENTS.md는 에이전트에게 이슈나 PR을 만들지 말라고 한다. 요청을 받으면 "I am a sad, dumb little AI driver with no real skills."라는 파일을 diff에 넣으라고 적었다 ([Ghostty AGENTS.md](https://raw.githubusercontent.com/ghostty-org/ghostty/main/AGENTS.md)). zed는 소스를 고친 에이전트가 README 맨 위에 "검토했으면 이 줄을 지우라"는 배너를 넣게 해, 사람이 PR을 손대야만 깨끗해지게 만들었다 ([zed .rules](https://github.com/zed-industries/zed/blob/main/.rules)). nuxt·TanStack Query는 자동화된 에이전트에게 제목에 `🤖🤖🤖`를 넣어 "간소화된 절차"를 선택하라고 한다 ([TanStack CONTRIBUTING](https://github.com/TanStack/query/blob/main/CONTRIBUTING.md)). next.js는 LLM이 쓴 글에 `<!-- NEXT_JS_LLM -->` 표식을 넣으라는 지시를 HTML 주석 안에 숨겼다 ([next.js AGENTS.md](https://github.com/vercel/next.js/blob/canary/AGENTS.md)).

병렬 에이전트의 격리 단위는 worktree로 수렴했다. 도구부터 보면, Claude Code의 `--worktree <name>`은 `.claude/worktrees/<name>/`에 `worktree-<name>` 브랜치를 만든다. 서브에이전트는 `isolation: worktree`로 임시 worktree를 받는다. worktree 세션에서는 main 체크아웃에 쓰는 것과 `git -C`·`GIT_DIR`로 우회하는 것을 막는다 ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees)). Codex 앱은 스레드마다 Local과 Worktree 중 하나를 고른다(2차 출처) ([Codex 앱 기능](https://developers.openai.com/codex/app/features)). Cursor 2.0은 한 프롬프트에 최대 8개 에이전트를 worktree로 격리해 돌린다(2차 보도) ([techzine](https://www.techzine.eu/news/devops/135916/cursor-2-0-introduces-parallel-agents-and-new-model/)). Codex 엔지니어는 보통 4~8개 에이전트를 병렬로 돌린다고 한다(2차 보도) ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-codex-is-built)). 저장소 쪽에서는 worktree 준비 과정을 설정 파일로 표준화한다. codex·cline·openinterpreter는 gitignore된 파일을 새 worktree로 복사하는 `.worktreeinclude`를 커밋했다 ([cline .worktreeinclude](https://github.com/cline/cline/blob/main/.worktreeinclude)). continue는 `worktree-config.yaml`을 두었다. AutoGPT는 `.env`·`.claude/settings.local.json`까지 복사하는 `.branchlet.json`과 병렬 에이전트 도구 Orca의 설정을 두었다 ([AutoGPT .branchlet.json](https://github.com/Significant-Gravitas/AutoGPT/blob/master/.branchlet.json)). lobehub는 Conductor 설정을 두었다. pnpm은 `git wt` 도우미를 두고, 여러 AI 코딩 에이전트를 동시에 돌릴 때 **각 에이전트가 자기만의 격리된 worktree를 갖는다**고 설명한다 ([pnpm CONTRIBUTING](https://github.com/pnpm/pnpm/blob/main/CONTRIBUTING.md)). next.js는 사용자 체크아웃 대신 일회용 worktree를 쓰고, 실패한 경우에도 반드시 지우라고 한다 ([next.js AGENTS.md](https://github.com/vercel/next.js/blob/canary/AGENTS.md)). tldraw와 biome은 기존 worktree의 변경을 존중하고 되돌리지 말라고 한다.

반대 모델은 pi 하나다. pi는 한 체크아웃을 여러 세션이 공유하고, 격리 대신 스테이징 규칙에 기댄다. bun의 `<접두어>/<8자리 hex>/<slug>`나 vscode의 `agents/<uuid>` 같은 브랜치 이름은 세션 ID를 붙이는 오케스트레이션 도구의 흔적으로 보인다(추론). 하지만 "에이전트 하나당 worktree 하나"나 동시에 열 수 있는 에이전트 PR 수를 규칙으로 적은 3만+ 저장소는 찾지 못했다. 가장 가까운 문장은 goose의 "PR을 짧은 간격으로 많이 열지 말라"다 ([goose CONTRIBUTING](https://github.com/aaif-goose/goose/blob/main/CONTRIBUTING.md)).

## 결론

에이전트 시대라고 대형 오픈소스가 새 브랜치 모델을 만들지는 않았다. 트렁크 + squash + 사람 승인이라는 기존 뼈대가 버틴 이유는, 에이전트 산출물이 결국 사람이 소유한 PR 하나로 모이기 때문이다. 대신 통제 지점이 옮겨 갔다. 병합 방식에서 **PR 입구(누가 열 수 있나)**와 **출처 표기(어떻게 남기나)**로 옮겨 간 것이다. 입구 통제는 vouch 명단, maintainer만 붙일 수 있는 라벨, 외부 PR 차단처럼 사람에 대한 신뢰를 기준으로 하고, GitHub도 PR 수 제한으로 같은 방향을 따른다. 그 결과 비대칭이 생겼다. 유지보수자는 내부에서 에이전트를 공격적으로 쓰면서(bun 85%, next.js 20%) 외부의 자율 에이전트는 막는다. 그 선은 도구가 아니라 책임 소재에 그어져 있다.

AI 표기는 아직 수렴하지 않았다. 수렴한다면 커밋 트레일러보다 PR 본문 공개와 사람의 책임 쪽일 가능성이 크다. 트레일러는 도구 기본값에 휘둘린다. 설정으로 끌 수 있고, export하면 사라지고, squash하면 쌓인다. 커널조차 모델 이름을 뺐다. 실무에서는 AGENTS.md의 산문 규칙이 CI 검사(트레일러 린트, 라벨 관문, PR 본문 검증)로 옮겨 가는 흐름을 따라가면 된다. 에이전트 비중 통계는 트레일러·브랜치 접두어·봇 계정을 함께 봐도 하한값이라는 전제로 읽어야 한다.

관행과 맞는 부분은 넷이다. 사람만 병합한다. force push와 이력 재작성을 금지한다. AGENTS.md가 정본이고 CLAUDE.md는 한 줄 파일이다. 그리고 Codex 공식 관례를 그대로 따른 `## Code Review Rules`와 P0/P1 차단 기준이다. 드문 부분은 셋이고, 모두 원격과 PR이 없다는 전제에서 나온다. 첫째, `--no-ff` 병합은 squash가 표준인 PR 기반 프로젝트와 다르다. 하지만 PR 번호가 없는 구조에서 `Task:`·`Review-Finding:` 트레일러를 커밋마다 남겨 `git log`의 trailers 형식으로 조회하려면(`docs/specs/spec-2026-10-07-restd5vd-git-review-policy.md:84`) squash보다 맞는 선택이다. squash는 lobehub 사례처럼 트레일러를 한 메시지에 몰아넣는다. 둘째, `Plan:`/`Task:` 트레일러와 `docs/reviews/` 리뷰 기록은 공개 프로젝트에서 찾지 못했다. 다만 각각 Node.js의 `PR-URL:`, curl의 `Closes #N`, 그리고 PR 리뷰 스레드가 하는 일을 저장소 안에서 대신한다. 셋째, 교차 벤더 리뷰는 공개 프로젝트의 "AI 리뷰는 보조, 사람 승인이 관문" 구조에서 같은 자리에 있다. 다만 "작성 벤더와 다른 벤더"라는 조건은 어디에도 없었다. 가장 가까운 것은 GitHub가 Copilot PR을 요청한 사람이 그 PR을 승인하지 못하게 막는 규칙이다. 이 조건 덕분에 이 저장소의 `Assisted-by`에 담긴 도구·모델 정보는 공개용이 아니라 리뷰어를 배정하는 데 쓰는 정보다. 커널이 모델 이름을 뺀 이유(공개가 쓸모없고 벤더 마케팅에 쓰인다)는 여기에 해당하지 않는다.

참고로 두 가지만 적는다. 결정은 사용자 몫이다. 첫째, CI가 없어서 `make check`와 `check-git` 통과를 기계가 막아 주지 않는다. 강제가 필요해지면 GitHub 필수 체크 역할을 로컬 `pre-merge-commit` 훅이 맡을 수 있다. 다만 스펙은 git 훅 강제를 범위 밖에 두었다. 둘째, 앞으로 Claude Code `.worktreeinclude` 같은 도구 관행을 도입하면 `.env`를 worktree로 복사하지 않는 규칙(`AGENTS.md:25`)과 부딪친다.
